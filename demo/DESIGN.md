## 1. 目标与成功标准

演示者在一台准备好的 Windows 电脑上启动本地服务，浏览器打开后即可完成“说明想玩的游戏和期望体验—检查本机信息—整理资料—生成游戏卡—查看优化方案—确认采用—性能测试—体验反馈—调整与对比—历史恢复”。设备检查可在需求提交前后独立执行；首次使用没有预置游戏卡。全程不依赖网络、模型账户、真实硬件读取或游戏进程。

这里的“保留原项目功能”定义为保留面向玩家的功能与操作语义：每个模块有可进入的页面、有有效输入和结果，并能串成闭环。项目已有的采集 CLI 与正式后台继续保留；演示服务独立表达这些功能，不以占位按钮或只有截图替代操作。

演示版也覆盖正式设计中尚未实现的推荐和反馈环节，但使用预置知识与确定性规则。演示版的覆盖范围不表示正式项目的实现进度。

成功标准：

1. 当前唯一游戏使命召唤可从空白需求入口走完闭环；用户未提交需求前，不出现其游戏名、封面、案例选择器或预建卡片。
2. 三至五分钟可讲完使命召唤主线；具体用时不作为软件性能承诺。
3. 断网可用、刷新可恢复、服务重启可继续；一键重置、一键加载完成案例可随时救场。
4. 采用、修改、版本、会话、反馈和比较关系前后一致；固定内容不意味着任意输入均返回相同的成功结果。
5. 玩家页面简洁、文字正常渲染、不出现演示版信息及工程字段；开发文档、内部元数据和导出产物保留数据性质与隔离声明。
6. 本机检查一次返回主要设备字段，不连续追问固定配置中已有的信息；游戏版本和安装路径等未获得的信息不编造。

正式文档仅用于本次识别需要展示的功能名称与用户旅程；本设计中的技术取舍、简化规则、样例设置与界面不能成为正式开发参考。

### 2.2 固定内容与实际交互

可以固定：本机信息、使命召唤的游戏识别规则、来源文本、设置目录、推荐模板、反馈规则、样例帧数据、进度阶段和错误剧本。自然语言需求中的体验偏好与原话必须保存，不能被默认叙事覆盖。

必须真实工作：页面切换、参数校验、答案保存、任务启动/取消/继续、配置版本生成、会话绑定、文件上传、样例分析、比较、历史、导出、重试和重置。

以下边界始终有效：

- 推荐是建议；“确认采用”保存玩家声明，不写入任何游戏配置文件。
- 进度是演示脚本进度；不能用“已联网读取”“本机实测”等文案表示未发生的动作。
- 当前不提供第二款游戏或双显卡性能对比；旧版本遗留数据不能混入使命召唤的结果。
- 玩家页面使用中性的“资料”“优化方案”“测试结果”等措辞；不声称设置名称、技术支持或菜单路径已在真实游戏核验。
- 隐去页面演示字样不改变内部事实：静态设备数据仍记录为模拟来源，样例性能数据不能改写成真实探测或真实实测。

### 3.2 首次使用与游戏卡生成边界

首次使用指服务尚无用户创建的有效游戏卡，不以浏览器 localStorage 是否为空作为唯一依据。服务内部可以保有使命召唤的 fixture 和工作区，但内部预置资源不等于用户已添加的游戏。

- 首页主问题为“你想玩什么游戏，希望获得怎样的体验？”，输入框为空，示例仅用“告诉我游戏名称、画面偏好和遇到的问题”等通用提示，不预填具体游戏名。
- 首次打开不出现使命召唤或地平线的名称、封面、游戏选择器、推荐结果及预建卡片。用户已主动输入的游戏名可出现在自己的消息和 agent 确认中。
- “我的游戏”初始显示简短空状态“告诉我你想玩的游戏，资料整理后会出现在这里”，没有固定案例按钮。
- 提交需求后先保存需求，再显示确认与资料整理进度；只有整理任务形成有效知识结果后才发布游戏卡。
- 卡片生成后的主线为“优化方案 → 确认采用 → 性能测试 → 体验反馈 → 调整与对比”。卡片应先出现，再允许进入方案；推荐生成可以随后进行，不要求卡片发布时已有推荐结果。
- 已有游戏的再次访问从服务恢复卡片及当前步骤，不重新播放初次引导。相同游戏的新需求更新需求版本并保留旧方案关联，不重复建卡；不能将新偏好自动套到旧结论。
- 没说清游戏或体验时，集中询问一到两个必要问题。未支持的游戏保存原话、说明当前尚不能完成该游戏分析，不偷换成使命召唤，不生成成功卡片。
- 取消、失败或关键资料不足时保留对话和已完成成果，给出继续或重试；不提前显示一张内容完整的游戏卡。

### 3.3 检查本机信息

本入口已按用户要求采用固定数据，不实现系统查询、CIM、命令行、浏览器硬件指纹或额外安装。按钮名称统一为“检查本机信息”，无需用户逐项填写主要设备配置。

| 展示字段 | 固定值 |
|---|---|
| CPU | Intel Core i7-14650HX |
| 显卡 | NVIDIA GeForce RTX 4060 Laptop GPU |
| 内存 | 16 GB |
| 显存 | 8 GB |
| 显卡驱动 | 621.01 |
| 操作系统 | Windows 11 专业版 |
| 桌面分辨率 | 2560×1600 |
| 显示刷新率 | 165 Hz |

交互约定：

1. 需求输入区域旁提供检查入口；检查前用“尚未检查”概括，不列出大量“未知”。提交需求时尚未检查，可由同一流程调用已有 `device.check` 动作，并简短展示检查状态。
2. 点击后立即显示“正在检查…”，按钮禁用防止重复提交；完成后显示“设备信息已就绪”和紧凑摘要“RTX 4060 Laptop · 16 GB 内存 · 165 Hz”。全部字段放入“查看设备详情”。
3. 失败时保留已有结果，提供重试，不将设备信息全部清空；已有相同字段时不生成无意义的新背景版本。
4. 固定数据保存在服务端，刷新或重启后可恢复。检查设备不创建游戏卡，也不自动填写游戏需求。
5. 不改动游戏名、游戏输出分辨率或已保存的体验偏好。桌面 2560×1600 不能覆盖游戏输出 1920×1080。
6. GPU 型号保留 Laptop 字样。现有桌面 RTX 4060 模板不能在匹配时被静默视为同一设备；需要条件确认时只给出相关的简短确认，不重问已有硬件字段。
7. 已有原始快照、推荐与测试记录保持不变；必要的设备更正生成新快照并复核适用性，不能改写历史。

现有 `device.check` 已支持固定字段返回、快照保存与重复检查复用；入口移入对话首页、设备详情默认收起及需求自动复用仍属于本次改版目标。内部保留 `origin=simulated`，玩家页面不显示固定样例或模拟实现说明。

### 3.4 背景编辑与现场游戏

背景、设备更正、安装信息补充放入详情操作，不占据首页。修改 GPU 或游戏分辨率后生成新背景修订，并复核当前方案；未知条件不能自动标为已适配。保留手动补充、明确不知道和稍后更正能力，但不重复追问检查结果已有的字段。

演示者可自行运行真实游戏。服务不启动游戏、不读真实设置、不采集现场 FPS，也不把游戏运行状态作为数据来源证明。页面不放常驻演示横幅，内部数据与导出保留来源性质；现场真实 FPS 与本服务的结果没有自动绑定关系。

## 5. 主演示流程

### 5.1 从零开始的一次闭环

1. 首次进入首页，看到通用需求输入框、检查本机信息入口和空的“我的游戏”。
2. 用户输入“我想玩使命召唤：现代战争 I，希望交战时少卡顿，同时保持画面清晰”。agent 保存原话，概括为“交战流畅优先，保留清晰度”；没有检查设备则复用检查动作获得固定信息。
3. 显示简短资料整理进度；内部执行发现、读取、提取、校验、补查、整理，各阶段有实际保存的成果。完成后发布使命召唤游戏卡，展示设备、体验目标和“资料已就绪”，主按钮“查看优化方案”。
4. 打开方案页，查看一句话方案摘要与主要调整；生成方案期间显示进度，完成后按需展开完整设置、依据、适用条件及替代调整。
5. 保存原配置 A0，确认已手动设置后采用主方案 A1；主按钮为“确认采用”，临近说明“请先在游戏内完成设置”。不声称已自动修改游戏。
6. 确认简短测试计划，点击“开始测试”；内部创建会话、区段和采集任务。默认约十二秒等待，样例数据时间轴为六十秒；页面分别展示“处理进度”和“数据时长”，不把等待时间当成现场采样时间。
7. 结束区段并生成首轮摘要 S1；在复测之前保存比较协议 P1，冻结共同阈值与基线引用。
8. 提交卡顿反馈和画质保护项；系统按模板给出 ChangeSet C1，明确原值、新值、理由、复测方法与恢复方式。
9. 点击“我已手动调整，确认记录”，从 A1 合并生成 A2；创建第二次会话，模拟复测生成 S2。
10. 使用 P1 比较 S1/S2；展示统一口径下的差异及可比条件，单独询问是否接受画面与操作体验。
11. 保存“保持当前方案”或“拒绝并恢复”。恢复生成 A3，不能把当前指针直接改回旧记录且删除 A2。
12. 历史页展示背景—来源—推荐—采用—会话—摘要—反馈—变更—比较—结果链；导出带标识的演示报告。

其中 A0/A1/A2、S1/S2、P1/C1 是讲解用代号，真实演示 ID 由服务生成，不要求演示者手填。

### 5.2 完成案例一键加载

开发者准备工具保留“加载完整案例”。它一次性生成使命召唤的完整有效历史、样例原件和报告，明确写入 `origin=demo_seed`，不回放等待动画。该工具不出现在玩家导航、顶部工具栏或更多菜单中，不能在首次打开时自动执行。

加载分为“完整历史，当前位于推荐后”和“完整历史，当前位于复测结果”两个快照位置；二者拥有对应合法对象。仅显式使用开发者工具时可连同需求和游戏卡一起生成。重复加载同一请求不能叠加重复会话；替换前确认范围，不改动正式项目或遗留归档数据。

### 5.3 开发者运行模式

下列配置仅供演示准备，不在玩家页面显示模式名称、剧本、推进阶段或跳过按钮。

| 模式 | 行为 |
|---|---|
| 讲解模式，默认 | 资料收集约八秒、推荐约三秒、模拟采集约十二秒，阶段可见 |
| 快速模式 | 每个异步任务约一秒结束，仍写入完整阶段与结果 |
| 分步模式 | 演示者显式点击“推进下一阶段”；只有该变更操作推进，查询不推进 |

时长是可配置演示脚本参数，不代表真实工具或模型速度。“跳到完成”仍验证前置对象并写阶段事件，不跳过必需输入或伪造已采用。

### 5.4 对话、研究与建卡状态

下表是待实现的交互契约；字段名为设计建议，不表示当前接口已具备。

| 状态 | 页面表达 | 可执行动作与转换 |
|---|---|---|
| 未提交需求 | 通用问题、空输入、设备入口、游戏库空状态 | 输入并发送，创建需求记录 |
| 需要补充 | 简短说明缺少游戏名或体验目标 | 回答后继续；不发布卡片 |
| 正在整理资料 | 用户需求摘要、当前阶段及已获得资料数 | 可取消；任务完成后验证发布条件 |
| 等待必要信息 | 指出阻塞的一个问题，保留已完成成果 | 回答或明确跳过；不可用条件仍阻塞建卡 |
| 失败或已取消 | 原需求及可恢复成果、具体原因 | 重试或继续，沿用同一需求；不建空壳卡 |
| 资料就绪 | 发布唯一游戏卡，保留对话中的完成消息 | 查看优化方案；非关键缺口进入详情 |
| 已有方案及后续流程 | 卡片显示当前步骤、当前方案和最近结果摘要 | 进入对应主动作，不强制重走研究 |

发布条件：用户已明确选择受支持游戏、已保存体验目标、关联整理任务已完成且存在有效知识快照。任务部分完成或关键条件未闭合时不发布卡片；非关键缺口可以保留在详情中。整理完成不能被前端计时器或装饰性进度条代替。

需求记录至少保存原话、规范化游戏标识、体验偏好、保护项、当前状态及关联任务。游戏卡至少关联需求版本、背景快照、知识快照、当前流程状态及现有方案/结果引用。设备快照独立于游戏卡，支持先检查后提出需求。

建卡发布应以规范化游戏标识做唯一性检查，并与需求、知识引用一起持久化；相同请求重试返回同一卡片。刷新和服务重启从服务恢复对话、任务、卡片及当前步骤。localStorage 只记视图偏好，不决定卡片是否存在。新偏好保留新需求版本，旧方案仍指向旧需求与背景。

## 6. 页面与交互设计

### 6.1 全局框架

采用以需求对话为入口的本地应用工作台。首次首页的视觉中心是需求输入，设备状态和“我的游戏”作为辅助区域。顶部只保留产品名称、必要导航和简短设备入口，不设置案例选择器、演示横幅、模式标签或开发者控制按钮。

一级导航收敛为“与助手对话”“我的游戏”“历史记录”；首次没有游戏卡时，后两项使用空状态，不泄露内部默认案例。进入卡片后显示“优化方案、性能测试、体验反馈、调整与对比”的步骤导航。现有知识、配置、日志与报告功能分别归入“资料与依据”“设置详情”“测试详情”“历史与报告”，通过详情页、抽屉或更多操作进入。

每个主视图同一时刻只有一个突出主按钮；次要动作使用文字或弱强调按钮，破坏性操作放入更多菜单并确认范围。步骤未满足前置条件时展示一句原因和必要入口，不平铺一整屏无法使用的表单。

视觉使用浅色中性背景、深色文本与单一青绿色强调色；数值使用等宽数字，图表以文本和线型区分。布局以 1366×768 和 1920×1080 讲解屏幕为主要验收尺寸，窄屏转单列，表格允许局部滚动。

字体使用本机中文无衬线与系统字体回退；图标、图表和示意资源本地保存，不依赖在线字体、CDN、游戏封面下载或真实游戏截图。游戏卡以游戏名、设备和目标建立识别，不强制添加装饰图或营销区域。

### 6.2 页面职责与渐进展开

下表定义改版后的职责，不要求继续以六个等权导航项同时展示所有模块。

| 页面或区域 | 默认可见内容 | 主操作及详情入口 | 必须出现的状态 |
|---|---|---|---|
| 与助手对话 | 通用需求输入、近期消息、紧凑设备状态 | 主按钮“发送”；检查本机信息、编辑需求、查看资料 | 空白、待补充、检查中、整理中、失败/取消、完成 |
| 我的游戏 | 研究完成后创建的游戏卡 | 主按钮随阶段显示“查看优化方案”“继续测试”或“查看结果” | 空列表、资料就绪、方案就绪、待测试、待反馈、已完成 |
| 资料与依据 | 一句话整理结论、资料数、必要缺口 | 查看来源；高级区保留指定采集、导入、预算、补查、取消/继续 | 进行中、等待输入、部分完成、完成、已取消、需复核 |
| 优化方案 | 目标、方案摘要、主要变化、适用性提示 | 主按钮“确认采用”；展开完整设置、替代方案、来源、基线和版本操作 | 生成中、条件待定、缺少依据、可采用、已采用、需复核 |
| 性能测试 | 当前方案、简短计划、测试状态；完成后显示关键指标与曲线 | 主按钮按状态切换为开始、结束或查看结果；详情保留切段、上传、绑定与比较协议 | 无配置、配置未知、进行中、样本不足、结果就绪 |
| 体验反馈与调整 | 满意度、一个问题输入、画质保护项及下一动作摘要 | 提交反馈、确认调整或复测；按阶段只突出一个动作 | 待反馈、待测、可调整、需补查、无改善、已停止 |
| 历史与报告 | 中文时间线、版本标签、配置变化及最近结果 | 查看版本、差异、回滚与导出；补录、补绑、备份恢复进入更多操作 | 空列表、当前版本、历史版本、原件不可用 |

游戏卡最多默认展示游戏名、设备摘要、体验目标、当前状态和一个主按钮。详细设备、来源列表、完整设置和测试原始表格不塞入卡片。对话只给出结论和下一步，避免同时复制整份方案。

方案页默认显示三至五项主要调整及一句简短原因；“查看全部设置”保留完整目录与至少十二项可操作设置。设置详情包含原名、菜单分组、建议值、当前声明值、变化、理由、依赖/重启条件和证据。未知项不填成已知，关键依赖和必须确认事项不得因折叠而隐藏。

结果页默认展示平均帧率、流畅度或卡顿指标与一条可读曲线。建议目标、资料参考和测试结果分区表达，不能混为一项保证。数值表按需展开；FPS、ms、秒、簇/分钟和百分比明确标单位。

### 6.3 反馈与错误体验

- 任务执行展示阶段骨架与状态文本，按钮防止重复提交；支持取消，不用无限转圈代替等待输入。
- 首次进入各页有可执行空状态，例如“告诉我你想玩的游戏”或“先完成一次测试”；不暴露预置游戏名或要求玩家理解样例加载。
- 失败在输入或相关面板附近显示，保留草稿，给出重试、补充、恢复预设或查看部分成果。
- 任务完成、保存或错误以适量提示通知；刷新后不重复弹出所有旧通知。
- 键盘可操作，表单有标签、焦点可见；对话框关闭回到触发按钮；尊重减少动态效果设置。

### 6.4 布局与文字密度

- 内容容器建议最大宽度 1200px，宽屏页面边距 24–32px，窄屏 16px；主要区域间距 24px，卡片内边距 20–24px，避免靠连续边框和嵌套卡片堆出层级。
- 正文默认 15–16px、行高约 1.6，辅助文字不小于 13px；标题、正文、辅助文字保持明确层级，不能把整段技术说明作为副标题。
- 主标题下说明通常不超过两行；agent 单次完成摘要以两至四个要点为宜，长正文和完整资料进入详情，不机械截掉用户原话或关键结论。
- 首页以输入区域为中心，保留留白；设备摘要与游戏库在其附近分层排列。1366×768 下需求入口和发送动作无需横向滚动即可操作；已建卡页面先看见当前状态和下一步。
- 宽屏可用主内容加辅助详情布局；低于约 900px 转单列，窄屏导航收敛。表格在自身容器滚动，页面整体不产生横向溢出；抽屉不能遮住必要确认或关闭按钮。
- 不一次展开长来源正文、完整配置表、日志上传表单、反馈表和全部历史。折叠内容必须有清晰入口，不能通过隐藏删除原有业务功能。

### 6.5 内容渲染与中文展示

当前存在文字未正确渲染的问题，本次要求按内容类型统一处理：

| 数据类型 | 展示规则 |
|---|---|
| agent 和资料中的 Markdown | 支持段落、标题、粗体、有序/无序列表、引用、表格和行内代码；不直接显示 Markdown 控制符 |
| 配置、设备等结构化对象 | 映射为字段列表或表格，使用中文名称和单位；禁止直接转字符串出现 `[object Object]` |
| 状态与动作枚举 | 统一映射中文状态与按钮文案，不能把 `waiting_input`、`needs_confirmation` 等原值直接显示 |
| 空值、缺失值与布尔值 | 空值按语义显示“尚未检查”“待补充”或“暂无结果”；布尔值映射中文，不显示 `undefined`、`null` 或无意义的零 |
| 设置差异 | 明确展示“原值 → 建议值”，依赖和必须确认事项就近提示 |
| 错误与恢复 | 说明当前操作为何未完成、已有成果是否保留，以及一个可执行恢复动作；不直接输出堆栈和接口错误对象 |

渲染层应有统一入口与状态字典，避免各页面自行拼接原始字段。支持的 Markdown 必须正确渲染；不支持的结构以安全纯文本保留，不能丢失内容。转义 HTML、禁止脚本与事件属性、拒绝危险链接协议，不通过不受控 `innerHTML` 插入用户输入或资料。资源仍本地自包含。

原始 ID、epoch、revision、哈希、任务键、来源协议地址、接口名和原始 JSON 不进入玩家页面及详情抽屉。需要辨别历史时使用“方案 1”“调整后方案”和时间等业务标签，内部仍以固定 ID 关联。

### 6.6 玩家文案与开发者边界

网页标题、导航、页眉页脚、按钮、状态、通知、弹窗、帮助文字、来源标题和报告预览统一检查：不出现“演示版”“独立演示服务”“固定样例”“模拟数据”“mock”“fixture”“seed”等实现信息。玩家侧使用“检查本机信息”“正在整理资料”“开始测试”“查看结果”等自然表达。

不为隐藏实现信息增加虚假的事实声明：不使用“已联网检索”“已实际探测”“已自动修改游戏配置”“已证实性能提升”等文案。确认采用明确要求用户已在游戏内手动设置；比较仍展示条件限制与主观接受。

开发者声明继续保留在 `demo/` 文档、代码注释、内部 `demo_only` / `origin` 字段与下载产物中，正式开发禁用边界不变。下载文件不属于玩家页面去标识的范围；其中的数据性质说明按第 14 节保留。开发者模式、失败剧本和救场操作从玩家页面移出，不只是改名或默认折叠。

## 7. 演示内容与知识包

### 7.1 使命召唤来源包

使命召唤预置四份本地模拟资料：设置说明、整套配置、带条件测试表、版本/兼容性说明。来源 ID 带案例前缀，并使用 `demo://` 内部地址；玩家界面显示中性的资料标题，点击打开本地详情，不显示内部协议地址，不将其作为真实外链。模拟作者和内部 fixture 名不进入展示标题，不冒充真实作者或真实引用。

每份包含标题、模拟作者标签、内容块、表格、样例日期、来源修订、哈希、设置关联及局限。日期是样例内容时间，界面不称最近实际检索时间。至少一份资料带原始/转载关系，以演示转载不能算独立支持。

采集结果预置：有效记录、条件配置、未知设置、被隔离的错误引用、P1 缺口及补查修订。来源/接受/缺口计数从当前记录计算，不能用固定数字与展开列表矛盾。

“指定来源”在高级资料操作中选择内置资料，不要求玩家输入 `demo://` 标识。不接受真实 URL 后假装已经联网读取；输入外部 URL 时提示“当前无法读取此链接，可先保存为线索”，不得生成已读记录。

### 7.2 推荐模板

使命召唤拥有独立设置目录、资料基准、主方案及偏画质/偏性能替代差异，至少十二项设置，覆盖显示、纹理、阴影、反射、后处理与缩放等分组。具体名称和值在 fixture 内维护，玩家界面使用设置显示名，不显示“演示预置菜单”等实现说明。生成方案时关联用户需求，明确画质保护项。

DLSS、帧生成、HDR 等技术若出现，支持情况默认 `unknown`；界面显示“待确认支持情况”，只有资料条件明确的分支才提供条件化选项。不以 GPU 型号自行推断真实游戏支持，也不把模拟资料写成真实核验结论。

每条建议包含设置 ID、值类型（固定/条件/未知）、理由、证据、依赖、是否需要玩家核对，以及恢复所需旧值。选替代项后重算演示方案快照，不修改主模板或其他替代项。

自定义设置值可以保存为实际声明，但若超出预置取值或缺少来源，推荐适用性降级为待核对，不产生对应性能预测。修改多个设置后继续测试，比较只能描述差异，不声称验证单项原因。

### 7.3 资料导入与复核

演示知识包为 `demo-knowledge/1` JSON，含 `demo_only=true`、案例 ID、内容版本、来源、记录、缺口与哈希。导入先预览并校验案例/引用/类型，失败保留错误，不发布半份资料；同包指纹重复导入返回已有快照。

“模拟版本更新”发布新来源修订，并将依赖旧资料的推荐标为需复核；旧配置和摘要不改。点击重新核对生成新推荐快照，不能自动采用。

## 8. 状态、版本与持久化

### 8.1 核心对象

每个对象共有：`id`、`scenario_id`、`workspace_epoch`、`created_at`、`demo_only=true`、`data_origin`。ID 使用 `demo_<type>_<uuid>`，明显区别于正式项目 ID。

`data_origin` 取 `fixture`、`simulated`、`user_declared`、`uploaded_demo_file` 或 `demo_seed`；上传文件的存在不意味着其内容是已核验的真实测量。

| 对象 | 最小字段与关系 |
|---|---|
| ContextSnapshot | 游戏/GPU 标签、输出分辨率、未知字段、修订与适用性；用户编辑新建修订 |
| InformationRequest/Answer | 缺失字段、问题版本、回答/跳过项、原话、归一值、更正来源；回答不变成自动探测 |
| KnowledgeSnapshot | 包指纹、来源修订、记录、缺口、覆盖与可用性 |
| Recommendation | 固定背景/知识引用、主方案、替代差异、目标、参考、准备状态与复核状态 |
| AppliedConfiguration | 背景引用、父版本、来源、完整设置、预设、确认声明、变更/恢复关联 |
| Session/Segment/Binding | 开始/结束、活动段、运行条件、固定配置版本或未知、绑定修订 |
| TestPlan | 场景、条件、时长、重复次数、指标列表、版本；计划不证明已执行 |
| LogArtifact/Summary | 原件哈希、演示来源、时间映射、区段绑定、分析规则与指标 |
| ComparisonProtocol/Comparison | 冻结口径、阈值、基线、样例逻辑先后、前后摘要、差异和可比性 |
| Feedback/ChangeSet/Outcome | 原话/明确偏好、诊断假设、基于实际配置的差异、结果引用与接受情况 |
| Task/Event | 类型、阶段、输入、状态、模拟预算、固定成果引用、取消与恢复父任务 |

本次新增的需求记录（暂称 `GameIntent`）与游戏卡（暂称 `GameCard`）是待实现实体，具体字段应满足第 5.4 节。它们复用现有对象存储和事务，不另起正式数据库。对话消息保存角色、内容、时间及需求/任务引用；游戏卡只保存固定关联与当前状态投影，不复制整份知识、方案和结果。

### 8.2 数据库

使用 `demo/runtime/demo.sqlite3`，由演示服务首次启动创建。采用六类简单表，JSON 保存演示对象，不复制正式数据库结构：

- `workspaces`：每案例的 epoch、背景/当前配置指针、页面位置及模式。
- `entities`：不可变内容对象和固定版本快照；`scenario_id + epoch + type + id` 唯一。
- `tasks`：当前任务投影、阶段与调度时间。
- `events`：追加的业务/阶段事件，按工作区序号排序。
- `mutations`：操作键、请求哈希、状态与已提交原响应，用于双击/丢响应重放。
- `files`：演示受管理文件 ID、相对路径、哈希、类型及大小。

所有变更在显式事务中发布；后台工作线程与 HTTP 线程分别使用数据库连接，写入经单一应用锁协调。SQLite 查询用参数绑定，演示对象不执行任意脚本。

### 8.3 需要保持的规则

1. 当前配置按案例工作区隔离。新采用比较 `expected_current_id`；过时提交返回冲突，不覆盖新版本。
2. 推荐生成不推进当前配置；手动确认采用才推进。补录过去配置只新建历史事实。
3. A2 来源于 A1 与具体差异的合并，未知设置和预设保留；回滚生成新版本并关联恢复目标。
4. 开放段不得分析；切段在同一边界结束旧段并绑定新段。历史补绑产生新绑定修订，不修改旧摘要。
5. 跨案例、跨 epoch、错类型或不存在引用均拒绝。修改背景后不能自动迁移旧样例的适用结论。
6. 查询无副作用，任务轮询不驱动阶段；重复操作键相同内容回原结果，不同内容返回冲突。
7. 同一案例只执行一个重任务；等待输入释放执行槽，取消保留已发布成果。
8. 重置递增 epoch；旧页面提交和旧任务后续写入必须失效，不能把结果灌入新工作区。

### 8.4 任务状态与恢复

任务状态：`queued → running → completed/partial/failed/cancelled`；`running ↔ waiting_input`。终态不原地复活，显式继续创建关联父任务的新任务，复用已发布阶段成果。

默认采集阶段为发现、读取、提取、校验、补查、整理。每阶段的耗时、模拟调用预算和新增对象由 fixture 指定；达到预算则部分完成，展示成果和未闭合缺口。

服务重启后，未完成任务标为中断且保留检查点，页面提供“继续整理”或“继续任务”。继续只推进剩余阶段，不能重复产生已发布来源。纯模拟采集的“租约”只关联任务和样例，不能出现伪造的真实 PID 或系统权限。

## 9. 性能数据与图表一致性

### 9.1 样例原件

使命召唤提供基线、首轮推荐、反馈调整后、无改善、样本不足五类确定性样例。每类需要重复展示时使用固定种子或固定文件，刷新不重新随机生成结果。

样例格式 `demo-frame-csv/1`：

```text
demo_only,scenario_id,trace_id,frame_index,timestamp_ms,interval_ms,frame_stream
true,mw2-rtx4060,demo_trace_a,0,0,,application_present
true,mw2-rtx4060,demo_trace_a,1,16.4,16.4,application_present
```

首行事件没有前一帧，间隔留空；后续时间戳累计对应间隔。只支持明确的 `application_present` 演示流，不模拟真实 PresentMon 全格式兼容。

约十二秒的处理等待与六十秒的数据范围分开记录。页面显示处理状态及“数据时长 60 秒”，曲线横轴使用相对时间；内部元数据及导出说明模拟时基，不声称该时轴映射到现场游戏时间或真实六十秒游玩。

图表、指标表、比较、下载 CSV 与报告必须引用同一原件哈希。不得用独立写死的 FPS 卡片配另一条随机曲线。

### 9.2 本地计算口径

以下是演示版自有说明与验证要求，不能作为正式算法实现参考：

- 保留的正且有限间隔为 `d1…dn`（ms）；平均呈现帧率为 `1000 × n / sum(d)`，不是逐帧 FPS 的算术平均。
- P95/P99 使用升序后的 nearest-rank；空样本返回未知，不返回零。
- 最慢 1% 取最大的 `ceil(0.01 × n)` 个间隔，指标为其均值倒数乘 1000；尾部不足二十个间隔时不展示该值。
- 自适应阈值为 `max(50 ms, 2 × median(d))`，仅用于本区段定位。
- 跨轮比较冻结一个共同阈值。长帧是严格大于阈值的间隔；连续长帧形成簇，坏行/时基断点切断连续关系。
- 长帧簇/分钟用有效时长作分母；长帧时间占比用长间隔之和除以有效间隔总时长；零分母返回未知。
- 坏数、倒退、重复时间戳与时间/间隔不一致需要记录限制并断链；真实尖峰不自动剔除。预热/加载排除必须显式给范围和说明。

主线样例应达到足够帧数与标称时长；不足剧本展示“样本有限”。展示用曲线可降采样，但保留峰值；统计一律从完整有效样例计算。文档不预写具体 FPS、百分比提升或 1% Low 数值，避免后续与原件不符。

### 9.3 比较资格

默认比较协议固定 50ms；可选择基于已闭合基线按上述规则派生共同阈值。协议保存后不可原地改，需新建。

只允许同案例、相同背景修订、相同输出/渲染条件和明确绑定的样例比较。变更项与预期不符、日志条件未知或事后建协议时降级为探索性差异，不能显示“已证实单项优化”。

模拟主线以演示逻辑事件保证协议先于模拟后测；页面称“前后对比”，不称真实受控实测。上传文件缺少可核验先后依据，默认探索性，不用上传时刻当采样时刻。

## 10. 反馈与下一动作规则

反馈表单包含：是否满意、症状选项、严重程度、场景、希望保留的画质项、自由文本、是否接受建议目标。自由文本原样保留，只有明确选项和有限关键词参与规则；未识别内容显示“需要补充”，不输出万能诊断。

| 条件 | 下一动作 | 演示输出 |
|---|---|---|
| 玩家满意且无新问题 | `keep` | 保留当前版本，记录接受，停止建议 |
| 无实际基线或没有可用性能数据 | `measure` | 保存反馈，建议完成基线/样例测试，不生成可执行变更 |
| GPU/设置身份/关键适用性未知 | `research` | 建补充问题或一次定向模拟补查 |
| 同案例卡顿，存在有效样例数据且有合法单项模板 | `adjust` | 基于当前配置生成一项设置或必要联动组的差异 |
| 明确保护项与默认调整冲突 | `measure` 或替代模板 | 保留保护项，说明替代方案/证据不足 |
| 连续两轮样例无改善或重复失败 | `stop` | 保留失败历史，建议保持/回滚/补充数据 |
| 输入超出规则覆盖范围 | `insufficient_evidence` | 保存原话，列待确认问题，不编造理由 |

ChangeSet 保存基准配置引用、原值、新值、假设、样例证据、测试计划与恢复清单。只有用户确认手动调整后才能生成新采用版本。

Outcome 分开记录“样例数据变化”“主观是否接受”“后续动作”。数值变好但用户不接受画面时，可以保存拒绝并回滚；不能把数值变化自动转成满意。

## 11. 接口设计

### 11.1 地址与通用约定

服务仅绑定 `127.0.0.1`，默认端口 `8765`，支持命令行改端口。所有静态资源与 API 同源；接口统一前缀 `/api/demo/v1`，不与正式 API 混同。

所有变更使用 `POST`，请求携带 `request_id`、`scenario_id`、`workspace_epoch`、`expected_revision` 与业务载荷。当前指针/问题/绑定等局部冲突另带对应预期 ID 或修订。请求保存到浏览器草稿后发送，双击和超时重试沿用同一 `request_id`。

成功响应包含 `demo_only`、请求 ID、工作区修订、结果引用；异步任务返回 202 和任务 ID。所有对象都由服务生成 ID，用户无需手填。

错误体为 `code`、用户可读 `message`、`field_errors`、`recovery_actions`；不泄露任意本地路径或 Python 堆栈。状态码：400 输入/格式错误，404 演示资源不存在，409 状态/版本冲突，413 文件过大，500 演示保存失败。

### 11.2 查询接口

| 方法与路径 | 用途 |
|---|---|
| `GET /health` | 返回服务版本、`demo_only=true` 与资源就绪情况 |
| `GET /bootstrap` | 改版目标：玩家启动信息、已创建游戏卡及设备摘要；不把 fixture 目录当作游戏库，不默认选中案例，不返回玩家模式标签 |
| `GET /workspaces/{scenario_id}` | 当前背景、指针、步骤与可用操作，不推进任何任务 |
| `GET /catalogs/{scenario_id}` | 该案例设置、来源、样例日志与模板目录 |
| `GET /entities/{id}` | 读取固定对象，校验案例/epoch，不隐式读取“最新替代版本” |
| `GET /tasks/{id}` | 查询状态、阶段、事件、缺口及已发布成果 |
| `GET /history?scenario_id=…&epoch=…` | 固定案例历史；按事件序号分页 |
| `GET /files/{id}` | 下载演示受管理文件，凭 ID 定位，不接受路径 |

上表路径均相对统一 API 前缀。

### 11.3 变更入口

使用一个 `POST /commands` 分发受控 `action`，减少临时服务路由数量；服务端用显式 action 注册表和逐动作字段校验，不能把 action 转成任意函数名执行。

| 动作组 | `action` 值 | 输入和结果摘要 |
|---|---|---|
| 背景与设备 | `context.save`、`device.check`、`device.scan` | 保存背景；固定整机信息检查；高级补充流程；新快照或任务 |
| 补充与更正 | `information.answer`、`information.amend` | 问题/两修订/回答或跳过；新回答与待问项，终态任务不复活 |
| 采集与知识 | `knowledge.collect`、`knowledge.import`、`knowledge.followup`、`knowledge.update` | 样例来源/预算或已上传包 ID；新任务或知识快照 |
| 推荐 | `recommendation.generate`、`recommendation.variant`、`recommendation.review` | 固定背景/知识/模板；新推荐或复核快照 |
| 设置与配置 | `setting.register`、`configuration.adopt`、`configuration.edit`、`configuration.rollback`、`configuration.record_history` | 设置声明、当前指针、父版本/恢复目标；新版本，历史补录不推进当前 |
| 计划与会话 | `plan.save`、`session.create`、`session.split`、`session.end`、`binding.revise` | 固定配置/计划/段绑定修订；新会话/闭合/修订 |
| 日志 | `log.inspect`、`log.associate`、`performance.analyze` | 文件 ID、区间/流/锚点、段或过去会话；预览、关联、任务/摘要 |
| 模拟采集 | `capture.start`、`capture.stop` | 活动段/样例类别；采集任务、样例原件与闭合段 |
| 比较 | `comparison.freeze`、`comparison.run` | 阈值模式/基线、协议与两摘要；固定协议、比较结果 |
| 反馈 | `feedback.save`、`preference.save`、`target.respond`、`feedback.next`、`outcome.save` | 原话/明确偏好/目标接受/固定配置与摘要；反馈、变更或下一动作、结果 |
| 任务控制 | `task.cancel`、`task.resume`、`task.advance` | 任务 ID/修订；取消、关联新任务或分步阶段 |
| 导出与备份 | `export.create`、`backup.create`、`backup.restore` | 固定引用/格式或演示备份文件；受管理产物或新 epoch |
| 演示控制 | `demo.mode`、`demo.script`、`demo.seed`、`demo.reset` | 模式/预设剧本/加载位置/范围；新控制状态或工作区 |

另设 `POST /uploads`，以有界 multipart 接收演示 CSV/知识包/备份，初版单文件上限 5MiB；上传后仅分配文件 ID，不自动发布知识或创建测量。未知格式保留副本与错误，可删除演示副本；不执行压缩包、不访问文件内路径。

单条 JSON 请求上限 1MiB；仅允许已登记 JSON 文件结构及演示 CSV。所有大小和错误都可复现，不以 HTTP 200 包含错误文本冒充成功。

### 11.4 本次改版的接口增量（待实现）

不改变现有命令事务、幂等键、epoch 和引用校验机制。新增需求与卡片能力可使用以下动作名，最终实施规划需与代码对齐：

| 接口或动作 | 责任与约束 |
|---|---|
| 需求提交，建议 `intent.submit` | 保存原话、游戏识别及偏好；不明输入返回待补充；受支持且信息完整时关联资料任务，不直接发布卡片 |
| 需求补充，建议 `intent.answer` | 更新需求版本，继续关联任务；不覆盖旧方案所引用的需求 |
| 任务完成时的卡片发布 | 服务端检查第 5.4 节条件后事务发布；不允许浏览器仅凭等待结束创建成功卡片 |
| 游戏库查询，建议 `GET /library` | 仅返回用户创建的有效卡片、当前步骤和可用操作；空库返回空列表，不能返回 fixture 列表 |

| `device.check` 的首页复用 | 现有动作已实现；改版需允许无可见游戏卡时调用，内部默认工作区不能导致玩家游戏库自动出现卡片 |

旧 API 中的开发者控制能力继续隔离于玩家流程；未支持的游戏标识不能通过直接提交旧案例 ID 进入地平线的活跃流程。新增动作、响应字段及上表建议路由在落地前都属于设计，不应在交接时称为现有接口。

## 12. 独立服务与目录结构

### 12.1 技术选择

- 后台：Python 3.11+ 标准库，Windows 本机优先使用 `py -3.13`。`ThreadingHTTPServer` 负责 HTTP，`sqlite3` 保存状态，单一工作线程推进模拟任务。
- 前端：原生 HTML/CSS/JavaScript ES modules，静态同源资源。暂不引入 React、Node 构建链或第三方图表库，减少演示前安装步骤。
- 图表：本地 SVG 或 Canvas，伴随数值表；前端只渲染后台摘要/曲线，不自行重算业务结论。
- 序列化与样例：JSON、CSV；不需要 API key、管理员权限或游戏安装即可展示。
- 持久化：演示专用数据库和受管理文件；浏览器仅保存当前页与未提交草稿，不承担领域真相。

这是为临时演示作出的技术选择，不决定正式产品的框架、模块接口或存储方式。

```text
  runtime/                  # 不入库：数据库、上传、导出、演示备份
```

### 12.3 启动与停止

现有启动命令为 `py -3.13 demo/server.py --port 8765`；脚本通过自身路径定位资源，与 shell 当前目录无关。双击入口检查 Python、启动并显示本地地址，窗口内 Ctrl+C 停止；不自动安装依赖、不后台启动可见的新控制台。

端口占用时明确报告并提示改端口，不结束已有进程。静态目录只公开白名单资源，不提供任意目录浏览。断网启动时无外部资源请求。

启动检查 fixture/schema/hash、静态文件与数据库可写性；错误时显示可操作诊断，不能悄悄换成空数据并宣布就绪。

## 13. 失败剧本与恢复

| 剧本 | 可见行为 | 恢复动作 |
|---|---|---|
| 设备字段未知 | 集中问题、已有结果保留、其他阶段可继续 | 回答、明确不知道、稍后更正 |
| 资料不足/预算不足 | 部分资料、P1 缺口、条件化方案 | 新轮模拟补查或增加演示预算 |
| 来源重复/坏引用 | 标记关联来源或隔离记录，计数匹配 | 查看理由、载入补查修订 |
| 任务中断/取消 | 任务终态与已发布成果可查 | 关联新任务继续剩余阶段 |
| CSV 不支持/数据损坏 | 保留上传副本、指出格式或行问题 | 下载合法样例、重新上传；不替换成默认成功结果 |
| 当前版本冲突 | 保留当前表单，展示新旧差异 | 刷新后重新确认，使用新操作键 |
| 样本不足/无改善 | 指标未知或结果无明显改善 | 补测、保持、回滚或停止，不强行展示提升 |
| 请求提交后响应丢失 | 页面保留原请求键和 unknown 草稿 | 查询或原键重试，只产生一份结果 |
| 原件丢失/保存失败 | 已有摘要可读但部分重算不可用，写入失败不推进指针 | 重载演示样例或恢复备份；不影响正式数据 |

失败脚本只作用于当前案例/epoch，默认关闭。选择和标识仅出现在开发者准备工具中，玩家页面只展示实际失败原因与恢复操作；取消剧本不应删除历史事实。

## 14. 导出、备份与重置

JSON 与 Markdown 报告包含：`demo_only=true`、案例/GPU/游戏标签、背景修订、来源性质、配置链、计划、样例原件 hash、统计口径、比较局限、反馈及接受情况。标题首行明确“演示报告，非真实实测”。

开发者工具保留当前工作区/全部演示工作区重置；操作前显示范围和将清除的数据。玩家页面不暴露案例重置工具。新 epoch 生效后中止旧任务，清空对应需求、卡片与流程视图，仅清理 `demo/runtime/` 登记的受管理文件。失败时不混用旧任务和新对象。不得访问或删除项目其他目录。

本次改版不得为了获得空首页而自动清库。旧版默认创建的工作区不能自动迁移为用户游戏卡；确有已完成任务与业务历史的使命召唤工作区可保留为“可恢复记录”，由用户主动恢复后建立关联。地平线历史留作内部归档，不进入玩家库；迁移前备份，迁移重复执行不重复生成卡片或历史。全新空状态演示使用独立数据目录或显式重置，不以刷新浏览器清除真实持久化记录。

### 17.1 对话节奏和视口

- 每次助手回复在提交后约 3 秒显示；先展示思考状态，暂时禁用重复发送。回复的可见时间存入服务端，刷新不会跳过等待。
- 最后一轮回复为“我先整理这款游戏的资料。完成后会把它加入‘我的游戏’，再生成对应方案。”随后展示“正在检索与收集资料”和约一分钟提示。
- 建卡时间不得早于上述回复可见后 60 秒，即提交后至少 63 秒。限制在服务端执行，快速模式和刷新均不能提前建卡；轮询可能带来少量显示延迟。
- 资料就绪后在对话中出现游戏卡，游戏库同步更新。同一游戏更新原卡，不重复创建。
- 对话页限制在视口内：标题和输入区固定，只有消息区上下滚动。刷新渲染保留阅读位置和输入草稿；窄屏输入区仍可见。

- 内部 `mw2-rtx4060`、原游戏 ID 和旧记录继续兼容，不以改显示名触发数据删除。存量文字在展示时统一格式化。
- 资料、设备背景、方案、测试、反馈及历史页提供“返回我的游戏”。删除“补充未知信息”面板；保留背景编辑和检查本机信息。
