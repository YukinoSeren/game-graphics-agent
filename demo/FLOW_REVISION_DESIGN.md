- 日期：2026-11-03。
- 设计版本：`demo-flow/2.0`。
- 文档状态：已授权实施的目标设计；实际完成情况与检查结果见 [实施与验证](./FLOW_REVISION_VERIFICATION.md)，不以设计目标替代验收事实。
- 适用范围：仅 `demo/` 独立离线服务，沿用 Python 标准库后端、原生 JavaScript 和现有 CSS。
- 初稿交付：设计文档与文档索引；用户随后已授权代码实施。初稿本身未修改业务代码、运行数据、现有视频或网页会话。

## 1. 目标与边界

将展示主线改为：**表达游戏与体验诉求 → 等待资料与方案同时整理完成 → 查看设备背景 → 查看 15 份资料 → 查看已有设置及详细依据 → 选择历史日志 → 提交体验反馈 → 等待 30 秒得到调整建议。**

所有资料、分析过程、方案、设备和日志继续由本地固定内容及规则驱动，不真正搜索互联网，不调用模型，不读取真实电脑配置或游戏日志。玩家页面不展示内部演示标识，开发文档、原始元信息和导出仍保留其模拟性质。

15 份资料中的平台名称用于固定资料的渠道分类。不能编造真实作者、文章原文、视频地址、发布日期或“官方验证”结论。页面展示预置的完整资料条目和站内详情；没有真实原文地址时，不提供虚构的外部原文链接。详细资料的要求通过充实本地正文与设置分析满足。

### 1.2 实现路线选择

| 路线 | 做法 | 取舍 |
|---|---|---|
| 仅前端延时与写死 DOM | 浏览器定时展示资料、推荐和反馈 | 改动少，但刷新、换页和直接调用接口会跳过等待，卡片与方案可能不一致 |
| **固定资料包＋现有服务端任务（采用）** | 扩充本地资料，在现有整理任务中生成方案，反馈新增持久化分析任务 | 延续现有架构，刷新恢复、引用关系和等待限制可统一验证 |
| 接入真实搜索和推理 | 动态采集、抽取与生成 | 不属于本次需求，不实施 |

## 2. 现状与修改原因

以下是设计时读取当前代码得到的落点，不代表已经修复。

| 当前实现 | 与目标的差异 | 修改方向 |
|---|---|---|
| `app/intents.py` 已有 3 秒回复、回复后 60 秒建卡期限 | 原结束回复仍说稍后生成方案，偏好未单独表达画面丰富度 | 调整对话文案与偏好映射 |
| `app/knowledge.py` 完成整理后发布资料和游戏卡 | 此时尚无推荐方案 | 整理任务发布阶段同时创建推荐并关联卡片 |
| 资料包目前 4 份，资料页预算上限也是 4 | 仅增加页面数字不能得到 15 份可阅读资料 | 数据包、载入校验、服务预算、页面一起调整 |
| 部分固定设置和来源存在未知、隔离或待复核内容 | 正常展示出现待核对与待核验标签 | 完整配置专用资料包，补足枚举和依据，隔离旧实验路径 |
| `pages/recommendation.js` 有生成入口，原因与依据分开 | 路径冗余，依据过短 | 展示已生成方案，统一依据抽屉 |
| `recent-logs.js` 用三张较大记录按钮 | 占用过多空间 | 原生 radio 单选组＋当前记录的一行摘要 |
| `feedback.save` 后直接调用 `feedback.next` | 立即返回建议，没有 30 秒分析阶段 | 引入持久化反馈分析任务和结果发布期限 |
| 页面进度部分依据是否存在 Feedback 判断 | 保存反馈并不等于建议已产生 | 改为依据分析任务及其结果判断 |

## 3. 完整演示流程与文案

### 3.1 首次进入与两轮对话

首次进入仍是通用助手页面，不提前出现使命召唤或其他游戏卡，不展示地平线内容。“检查本机信息”继续放在输入区附近，点击可查看并保存固定电脑档案。

第一条用户输入必须支持：

> 我想玩使命召唤现代战争1

助手约 3 秒后回复：

> 好的，你希望这款游戏带来什么样的体验？

第二条用户输入必须支持：

> 我想要在保证流畅的前提下 尽可能保证画面的丰富感

助手约 3 秒后回复：

> 我先整理这款游戏的资料，并根据你的设备和体验目标生成设置方案。完成后会一起加入“我的游戏”。

旧回复中的“再生成对应方案”容易让人理解为还要进入设置页操作，本轮替换为以上表述。

第二次输入继承上一轮游戏身份，不能要求用户重复游戏名。将诉求解析为：

- 首要目标：保持流畅，减少明显的帧时间波动。
- 次要目标：尽量保留材质、场景层次和战斗特效的丰富度。
- 优先保留项：纹理细节、纹理过滤、当前渲染分辨率。
- 调整策略：先平衡阴影、环境光遮蔽和反射；后续若反馈爆炸卡顿，优先局部调整粒子质量。

展示名统一“使命召唤：现代战争 I”。输入中的 `1`、`I`、`一` 视为同一游戏；内部旧 ID 保持兼容，不以改名删除历史。

### 3.2 等待中的展示

回复可见后进入约一分钟整理区，只出现一张进度块，避免持续新增聊天气泡。

```text
正在检索与收集资料
正在整理游戏设置、设备条件与画质取舍，预计需要约 1 分钟。

收集资料 → 整理依据 → 生成设置方案
```

“检索与收集”是本地预设流程的玩家用语；不展示虚构的实时外网抓取记录，不声称当前连接到某个网站。资料完成数量根据本地任务已完成的阶段展示，不能在资料尚未写入时固定显示“15/15 完成”。

完成后显示：

> 已整理 15 份资料并生成设置方案，这款游戏已加入“我的游戏”。

聊天中的卡片按钮为“查看我的游戏”。仍保持标题与输入区固定，只有聊天消息列表滚动；进度更新不抢走用户的滚动位置。

## 4. 一分钟内完成资料和推荐

### 4.1 时间口径

以第二条消息提交为 `T0`：

| 时刻 | 可见状态 | 服务端约束 |
|---|---|---|
| T0～T0+3 秒 | 助手正在回复 | 保存 `reply_visible_at`，未到时不展示最终回复 |
| T0+3 秒 | 展示整理说明，开始一分钟等待 | `card_not_before = reply_visible_at + 60s` |
| 随后 60 秒 | 资料收集、整理、方案生成进度 | 本地任务可提前计算，但不提前发布卡片与新方案 |
| 不早于 T0+63 秒 | 同时出现资料、方案与游戏卡 | 最终发布事务检查期限与完整性 |

沿用现有“助手回复后 60 秒”的口径，不能误改为提交后总共 60 秒。轮询与调度可带来少量显示延迟，文案使用“约一分钟”。

### 4.2 发布顺序与完整性

整理任务保留现有发现、读取、提取、整理等内部阶段。最终 `organize` 阶段在同一个发布事务内：

1. 校验 15 个来源条目均可载入，来源 ID 唯一，正文与设置引用完整。
2. 创建或最终确定 KnowledgeSnapshot，并记录资料包版本。
3. 调用可复用的本地推荐构建函数，创建 14 项完整主方案及其依据包。
4. 为保留旧的方案切换能力，可同时创建已有“偏画质”“偏性能”预设，放入折叠区；主线不需要点击生成。
5. 创建或更新 GameCard，写入 `knowledge_id`、`context_id`、`recommendation_id`、`source_pack_version`、当前目标。
6. 更新 Intent 为就绪，任务结果返回卡片、资料、主方案 ID，再发布完成消息。

前置条件不满足时整批发布失败，不出现“卡片已就绪但没有方案”的半成品。查询接口保持只读；不能在打开设置页时偷偷补生成。

在 `recommendation.py` 内抽取接受当前事务及背景、资料、目标的构建函数；现有生成命令与整理任务复用它。不要在事务中嵌套发起 HTTP 或新的 `service.command`，避免嵌套事务与部分提交。

### 4.3 刷新、重复提交与旧记录

- 服务端期限是唯一依据，快速模式、单步运行、刷新及重新进入页面均不能提前发布。
- 重复的命令请求复用现有 request ID 幂等机制。同一游戏更新原卡，不能重复建卡。
- 新浏览器从卡片恢复主方案，不能依赖旧浏览器的 localStorage 才找到方案。
- 暂停或中断任务后继续，保留原始期限；若期限已过，继续后可完成，不重新计满一分钟。
- 旧游戏卡若没有关联推荐，实施时提供显式兼容修复或引导重新与助手整理。不能在 GET 中产生推荐，也不伪装成新流程已完成。

## 5. 我的游戏、设备背景与导航

### 5.1 游戏卡

卡片保留游戏名、体验目标和精简状态：

```text
使命召唤：现代战争 I
流畅优先，尽量保留画面丰富度
15 份资料 · 设置方案已就绪

[查看设备与背景]
设备与背景 → 资料与依据 → 设置详情 → 游玩日志 → 体验反馈
```

首次完成的主按钮指向设备与背景。五个入口都可直接点击，推荐参观顺序不变成强制锁定。访问某页不应被当成用户已经采用设置或完成分析。

每个详情页保留“返回我的游戏”；底部按流程提供一个下一步按钮：

| 页面 | 主线下一步 |
|---|---|
| 设备与背景 | 查看资料与依据 |
| 资料与依据 | 查看设置详情 |
| 设置详情 | 查看游玩日志（采用确认按原业务约束保留） |
| 游玩日志 | 前往体验反馈 |
| 体验反馈 | 完成分析后查看调整建议或返回我的游戏 |

### 5.2 设备与背景

用两个清晰分区展示固定设备与目标，避免冗长解释和未知字段堆叠。

| 项目 | 固定展示值 |
|---|---|
| 处理器 | Intel Core i7-14650HX |
| 显卡 | NVIDIA GeForce RTX 4060 Laptop GPU |
| 内存 / 显存 | 16 GB / 8 GB |
| 系统 / 驱动 | Windows 11 Pro / 621.01 |
| 桌面显示 | 2560×1600，165 Hz |
| 游戏渲染分辨率 | 1920×1080 |
| 体验目标 | 流畅优先，尽量保留画面丰富度 |

桌面显示分辨率与游戏渲染分辨率分开，不能显示成互相冲突的同一个字段。未设置的可选安装目录、具体补丁号等不进入默认概览，不编造游戏版本号填满页面。

保留“检查本机信息”和编辑背景能力，删除“补充未知信息”板块。固定设备检查得到的是本预设完整背景，不应仅因被标记为 `custom` 就让所有方案变成临时待复核；背景匹配应比较实际条件和预设版本。用户编辑为其他设备时明确提示“背景已更新，请返回助手整理新方案”，不能继续假定旧方案适用。

## 6. 资料与依据：15 份固定资料

### 6.1 页面结构

默认进入完成态资料库，而非采集配置表单。

```text
资料与依据                                      返回我的游戏
已整理 15 份资料，覆盖设备条件、画质取舍与密集交战场景。

全部 15 | 官方说明 2 | NVIDIA 参考 2 | 小黑盒 3 | 知乎 3 | 贴吧 2 | YouTube 3

来源渠道 · 资料主题
两到三行摘要
关联设置：纹理细节、纹理过滤
[查看资料]
```

桌面端资料卡双列，窄屏单列。全部 15 份可滚动访问，筛选不改变总数。不要把完整正文直接塞进首页；正文放在站内详情抽屉，卡片摘要用于快速了解。

现有采集预算、手动启动、追问、导入及验证工具移入折叠的高级区域，不占据主线首屏。默认收集任务固定取完整 15 份，不能仍被 `max_sources=4` 截断。

### 6.2 资料条目规划

下表是**待编写的本地资料内容主题与摘要**，不是已获取的真实平台文章。`S01` 等为稳定引用键；渠道分类不表示真实发布或官方背书。

| 编号 | 渠道分类 | 资料标题 | 本地正文需要展开的内容 | 主要关联 |
|---|---|---|---|---|
| S01 | 官方说明类 | 运行条件与显示设置说明 | 区分设备条件、桌面分辨率和游戏渲染分辨率；说明显示模式与目标帧率的关系，解释为什么不能仅用显卡型号推导所有场景表现 | 显示模式、渲染分辨率 |
| S02 | 官方说明类 | 画质选项与场景层次 | 解释纹理、阴影、环境光遮蔽、反射和粒子的视觉作用；将“丰富感”拆为可观察的画面层次，说明不同设置不能用一个总画质档替代 | 纹理、阴影、遮蔽、粒子 |
| S03 | NVIDIA 参考类 | 呈现节奏、同步与操作响应 | 解释垂直同步可能带来的画面撕裂与响应取舍；强调显示器刷新率不等于实际游戏帧率，不加入未建模的 Reflex 等功能支持承诺 | 显示模式、垂直同步 |
| S04 | NVIDIA 参考类 | 显存预算与材质细节 | 说明纹理细节、资源驻留和连续游玩的观察方法；在固定 8 GB 档案中先保留高纹理，遇到持续加载问题时再评估，不能声称永远不会显存不足 | 纹理细节、纹理过滤 |
| S05 | 小黑盒类 | RTX 4060 的平衡预设思路 | 给出本地固定 1080p 平衡预设的选择顺序：纹理优先、次级效果适度降低；明确“流畅优先”和“所有选项最低”是不同目标 | 主方案整体 |
| S06 | 小黑盒类 | 材质、远景与画面丰富感 | 对比纹理细节与过滤对表面、斜视地面和远景的影响；解释保留这两项比同时堆高多种次级效果更符合本轮体验诉求 | 纹理细节、纹理过滤 |
| S07 | 小黑盒类 | 密集交战中的特效取舍 | 讨论烟雾、火花和粒子堆叠的局部开销；初始保留高粒子以兼顾丰富感，出现明确爆炸卡顿反馈时优先只降一档并回到相似场景复看 | 粒子、阴影 |
| S08 | 知乎类 | 平均帧率与帧时间波动 | 区分均值、长帧、分位数与主观卡顿；解释平均帧率尚可时仍可能在复杂场景卡一下，说明固定日志能支持观察却不能定位具体爆炸时刻 | 日志解读、反馈判断 |
| S09 | 知乎类 | 环境光遮蔽与反射的视觉收益 | 解释接触阴影和表面反射对空间感的贡献；比较中档与关闭之间的画面损失，用适度降低代替全部关闭以维持场景层次 | 环境光遮蔽、反射 |
| S10 | 知乎类 | 分辨率、抗锯齿与清晰度 | 说明几何边缘稳定性、渲染分辨率和纹理清晰度的区别；固定使用 1080p 与现有 SMAA T2X 预设，不把未知超分辨率支持当作已知功能 | 渲染分辨率、抗锯齿、超分辨率 |

### 8.2 完整示例：环境光遮蔽选择“中”

**当前选择：环境光遮蔽，中。** 你希望保留场景丰富感，因此保留物体接触处的阴影和深度线索；同时优先流畅，不把所有次级效果同时设为高。

**S02／官方说明类《画质选项与场景层次》**：本地条目解释了环境光遮蔽对墙角、物体接触处与细小结构层次的作用。完全关闭会削弱这类空间线索，因此不作为初始方案。

**S09／知乎类《环境光遮蔽与反射的视觉收益》**：本地条目比较了中档保留主要深度关系与高档细节收益之间的取舍，倾向在控制负载时先选中档。

**S13／YouTube 类《逐项画质对照的观察要点》**：本地观察笔记强调应在相同视角关注接触位置，不能只凭整体预设名判断效果。资料保留了提高画质的理由，也要求结合复杂交战场景复看。

**综合选择**：不采用关闭，因为它削弱本次强调的场景层次；暂不采用高，因为主方案已经优先保留高纹理和高粒子，应给密集场景留下调整空间。采用中档，接受局部细节精度降低。若后续反馈主要是爆炸时卡顿，先检查粒子相关取舍，不首先降低环境光遮蔽。

### 10.1 页面与输入

主区域突出一个体验描述输入框，支持原样输入：

> 爆炸时画面卡顿

保留按钮文字：**提交反馈并获取建议**。满意度、严重程度与优先保护项可放在“更多反馈选项”，采用合理默认值；不能要求额外填满一张表才能提交这句话。

### 10.2 等待状态

点击并成功受理后立即禁用重复提交，显示：

```text
正在重新分析你的体验反馈
正在结合当前设置、游玩记录与资料依据重新权衡，预计需要 30 秒。

理解反馈 → 对照记录 → 权衡调整
```

可以展示剩余时间估计，但服务端状态决定是否完成。先前的反馈结果收进历史，不与本次“正在分析”同时冒充当前结果。页面切换、刷新和换浏览器后均可恢复同一分析任务。

### 10.3 服务端任务设计

新增一个原子提交动作 `feedback.review`：保存 Feedback、创建 FeedbackAnalysis、入队分析 Task，一次返回任务 ID。避免前端先保存成功后第二次请求失败形成“看似已分析”的半成状态。

建议分析实体字段：

| 字段 | 说明 |
|---|---|
| feedback_id / task_id | 反馈和执行任务 |
| game_id / intent_id | 对应游戏及当前目标 |
| applied_config_id / context_id / summary_ids | 不可变输入引用或快照 |
| knowledge_id / source_pack_version | 本次采用的资料版本 |
| request_fingerprint | 相同输入重复提交复用任务 |
| accepted_at / ready_not_before | 受理时间与受理后 30 秒期限 |
| status | queued、running、completed、interrupted、failed、cancelled、superseded |
| change_set_id / result | 仅完成时发布 |

阶段示意：受理后理解反馈，约第 8 秒对照日志，约第 18 秒权衡设置，**不早于第 30 秒发布结果**。阶段时间用于本地展示，不描述为真实模型推理。

复用 TaskRunner 的 defer 机制，对反馈结果发布阶段增加期限检查。现有卡片期限检查不能被覆盖；两类任务分别遵守自己的发布时间。`fast`、`step` 和旧接口均不能绕过期限。

将现有反馈规则评估抽成不负责立即发布的内部函数，在任务最终阶段调用。旧 `feedback.next` 如需保留，改为接入同一个异步任务及期限逻辑；不能保留一个仍可立即产生 ChangeSet 的旁路。

在发布前再次核对配置、背景和输入摘要仍与分析快照一致。若用户期间采用了别的配置或改了背景，本任务标记失效，提示“配置已变化，请重新分析”，不把旧输入的建议套在新配置上。

### 10.4 固定结果与具体取舍

为“爆炸＋卡顿”配置高于通用卡顿规则的优先匹配，避免被旧的泛用降阴影规则抢先命中。

当前主方案下固定建议：

```text
建议小幅降低爆炸特效负担
粒子质量：高 → 中
保留纹理细节、纹理过滤和渲染分辨率。

依据：S07、S11、S14，并结合本次所选日志中的帧时间波动。
代价：部分爆炸、火花和烟雾细节减少，整体材质与清晰度保持。

[查看调整依据]  [记录已按建议调整]
```

建议说明必须区分观察与推断：

- 用户说明爆炸时卡顿；所选样例日志提供帧时间波动信息。
- 两者支持优先尝试降低密集特效负担的假设，但日志没有爆炸事件标记，不能写成“已定位第 X 秒爆炸导致卡顿”。
- 因为用户强调丰富感，所以先只降低粒子一档，保留材质和清晰度。
- 建议在相似交战场景复看长帧与观感，不能预告固定提升多少 FPS。

规则约束：每次最多调整一项；不得降低已保护的纹理、过滤或分辨率。若粒子已为中或低，优先选择允许且未保护的阴影降一档；无合法改动则返回具体复看建议，不产生空 ChangeSet 或重复调同一个值。若用户显式保护粒子，也必须遵守保护项。

“记录已按建议调整”继续沿用人工确认语义；不会自动写游戏设置。反馈后再次读取日志时要关联新确认的配置，旧记录和旧摘要保留原关系。

### 10.5 重复、刷新与失败

- 受理后重复点击返回同一任务，同一输入不重复生成结果。
- 同一游戏最多一个当前分析任务；提交不同反馈时，明确将旧任务标记为被替代，旧任务不能稍后覆盖新结果。
- 刷新从服务端恢复 `ready_not_before`，不重新开始 30 秒，也不依靠浏览器定时器提前完成。
- 服务重启沿用当前中断机制，页面提供继续分析入口；继续保留原期限。未恢复前不能一直假装正在运行。
- 第 29 秒不得存在对外可用的新调整结果；第 30 秒及以后，任务成功才显示结果，且只发布一次。
- 失败显示“重新分析未完成，请重试”；保留用户输入与旧历史。读取任务状态不会触发重试或规则执行。

## 11. 数据与接口修改设计

### 11.1 关系与恢复

```text
Intent → Context → KnowledgeSnapshot（15 个 Source）
                         ↓
                  Recommendation（14 项＋依据包）
                         ↓
GameCard ───────── recommendation_id
                         ↓ 用户确认
                  AppliedConfig → 日志摘要
                         ↓
Feedback → FeedbackAnalysis → Task → ChangeSet / 复看建议
```

使用现有实体存储机制，不新增正式数据库。客户端选择 ID 只是视图状态，不能取代服务端卡片和分析实体的业务关系。

### 11.2 接口与契约

沿用 `/api/demo/v1`、scenario、workspace epoch、request ID 和当前修订校验机制；以下为目标增量：

| 接口 / 动作 | 目标改动 |
|---|---|
| `intent.submit` | 支持两句输入与丰富感偏好，返回原有可见时间和整理任务引用 |
| 资料整理任务结果 | 同时返回 knowledge_id、card_id、recommendation_id |
| GameCard 实体 | 增加主方案 ID、资料包版本；恢复时可直接找到方案 |
| `GET /tasks/{id}` | 反馈任务可读取持久化阶段与发布时间；发布前无结果引用 |
| `feedback.review` | 新增一次性提交反馈与入队，返回 FeedbackAnalysis、Task 引用，接受后返回异步受理响应 |
| `feedback.next` | 兼容入口转为同一异步任务，不再立即给结果 |
| `log.capture_recent` | 协议语义不变，单选 ID 传入现有字段 |
| 健康 / bootstrap | 目标升级 `demo/1.3`、`ui_contract=conversation/2`，声明 `feedback.review` 与自动方案能力 |

具体响应 envelope 保持现有 command 格式；异步状态及 ID 放入现有 result/refs 位置，避免另造一套不兼容协议。前端必须校验新能力，发现旧服务提示重启，不能把旧接口成功当成新流程就绪。

### 11.3 固定资料与旧状态

- 新资料包版本建议 `mw1-richness/2`；来源、模板、规则与设置定义一起校验。
- 更新 `fixtures/manifest.json` 中所有被修改资源的校验摘要。
- 主方案 14 项必须都有合法值、至少两份相关来源和完整依据包；15 份来源必须都能打开正文。
- 新的普通流程不消费旧的未知超分辨率记录、资料隔离占位或缺失字段来生成表面完整的方案。
- 旧记录和旧导出保持原始模拟元信息，不批量“升级”为已核实资料。
- 实施和验收用新的临时演示数据目录；未经新的明确操作不清空当前网站会话、旧日志、既有视频或整个 runtime。

## 12. 前端视觉、文案与可访问性

沿用现有白底、青绿色强调和字体系统，不引入前端框架、字体 CDN 或额外依赖。调整目标是减轻首屏密度、统一层级，而不是重做品牌。

| 区域 | 设计约束 |
|---|---|
| 页面主体 | 最大内容宽度沿用项目容器；页面标题、短摘要、主要内容分层 |
| 资料卡 | 两到三行摘要后进入详情，长正文不默认铺开 |
| 设置卡 | 名称、建议值、一个依据入口；不重复放两套解释按钮 |
| 依据抽屉 | 按来源、分歧、决定分段，正文行高约 1.6～1.8，允许内部滚动 |
| 日志选择 | 一个单选组，一行选中摘要，一个读取按钮 |
| 反馈 | 一个主输入、一个提交按钮，成功后替换为分析状态或结果 |
| 动画 | 切页与抽屉约 180～240 ms 淡入/轻位移；单选约 120～160 ms；优先 opacity/transform |
| 等待阶段 | 阶段标签平稳更新，不使用持续大面积跳动；支持 reduced-motion |
| 焦点与键盘 | 原生按钮和 radio；抽屉支持 Escape、焦点约束与关闭后回到触发项 |
| 异步播报 | 用温和的 live region 宣告阶段和完成，不每秒播报倒计时 |

正常固定流程不显示：`待确认`、`待核验`、`待核对`、`需要复核`、`需要确认`、`资料未核实`。通过完整数据、明确适用性和面向玩家的展示字段解决，不做全局字符串删词，不抹去真实失败信息，不替换为“官方认证”“真实实测”等错误表述。

重点检查 `content.js` 当前将演示来源文字替换为待核验资料的逻辑；新资料使用明确 `display_blocks` 与渠道字段渲染，不能继续触发旧的占位替换。异常流程仍须如实提示中断、配置变化或任务失败。

## 14. 验收设计

### 14.1 服务端与数据检查

时间测试使用可控制时钟或既有调度测试机制，不以大量真实等待替代边界检查。

| 编号 | 场景 | 期望结果 |
|---|---|---|
| A01 | 依次提交两条原样输入 | 第二句继承游戏；目标包含流畅优先和画面丰富度 |
| A02 | 第二句后 2.9 秒 | 尚无最终助手回复 |
| A03 | 回复可见后 59 秒，含快速与单步模式 | 无新卡片、无对外发布的新主方案 |
| A04 | 回复可见后至少 60 秒，任务成功 | 卡片、15 份资料、14 项方案、依据包同时可用 |
| A05 | 第 15 条正文缺失或设置来源断链 | 任务不发布半成品，返回可理解的失败状态 |
| A06 | 全部来源与设置枚举检查 | 15 个唯一来源、六类渠道、14 项合法值；无 null 主方案值 |
| A07 | 清空浏览器选择状态后进入我的游戏 | 从服务端卡片恢复相同方案，不重复生成 |
| A08 | 重复命令 / 同游戏重新整理 | 不重复卡片；历史版本引用保持一致 |

| A11 | 旧 `feedback.next`、快速模式、重复提交 | 同样遵守 30 秒门槛，不产生旁路结果 |

| A15 | 相同日志＋相同采用配置重复读取 | 复用既有关系，不新增重复会话和段 |
| A16 | 中断、继续、刷新、取消 | 保留原期限，取消后不迟到发布，状态可恢复 |

### 14.2 浏览器人工流程

1. 使用独立空白验收状态打开助手，确认没有初始游戏卡。
2. 检查固定电脑信息，依次输入两句指定文字，观察 3 秒回复和约一分钟整理。
3. 期间刷新一次，确认期限不重置且不能提前查看新方案。
4. 游戏卡完成后按设备与背景、资料与依据、设置详情的顺序浏览；所有页面可返回我的游戏。
5. 验证 15 条资料数量及六类筛选，逐条打开正文；正文正确分段，来源不出现虚构外链或作者。
6. 设置页没有生成和重新生成按钮，也没有独立“为什么这样设置”；逐项检查依据来源与取舍。
7. 确认按方案设置的记录，进入游玩日志，键盘切换三项 radio，读取其中一次，验证显示来源。
8. 输入“爆炸时画面卡顿”，提交后看到 30 秒提示；期间换页再返回一次，不能立即得到结果。
9. 完成后检查单项调整、保留项、来源和复看建议；没有自动修改游戏或保证提帧的表述。
10. 在 1920×1080、1366×768 与约 390 px 窄屏检查：聊天输入区可见、资料不过密、抽屉可读、日志选择紧凑、radio 与返回按钮可操作。

正常主线截图及渲染文本检查应覆盖用户不希望出现的状态词；这些词可以存在于开发文档、旧历史原始记录或自动化断言中，不能据此全仓替换。异常流程单独验证，保证错误提示仍然真实有效。

### 14.3 后续录制衔接

本轮不重录视频。代码验收后再按以下展示顺序制作新版视频：两句对话 → 剪去一分钟等待的中间部分并保留时间过渡提示 → 我的游戏 → 设备与背景 → 15 份资料概览和一份详情 → 设置及一份综合依据 → 紧凑日志选择 → 爆炸卡顿反馈 → 剪去 30 秒等待的中间部分并保留提示 → 单项调整建议。

视频剪辑只缩短观看时间，不修改网页真实等待逻辑。是否沿用原 90 秒长度，在后续录制方案中处理，不在此处扩大代码范围。

## 15. 本设计采用的明确约定

1. 初稿阶段仅交付设计；用户随后已授权代码实施。实施不包含清空原会话或重录视频。
2. 资料全部预置；平台名是渠道分类，正文是本地内容，不冒充真实文章原文。
3. 首次等待口径仍为第二次回复出现后 60 秒，资料、方案与卡片一起就绪。
4. “前一次／前两次／前三次”分别选择一份过去的记录，不累计分析多份。
5. 爆炸卡顿默认先降低粒子一档，保留本轮强调的材质与清晰度；这是演示规则，不是性能诊断结论。
6. 正常主线去掉待核验类标签，通过补全资料和适用条件实现，保留内部模拟元信息与真实失败提示。
7. 前端保持现有技术栈和风格；原采用确认、历史、回滚、导出等功能继续保留在合适位置。

后续实施完成后另写实际修改与验收记录，再更新运行版本说明；不得把本设计中的目标行为直接写成已完成事实。
