# 01 设备、游戏与实际配置设计

> 推荐设计 v1.2；保留“自动获取失败后向用户提问补充”，新增独立基线、未知配置会话及调整采用链路。本章未实现部分不因写入文档而视为已支持。
>
> 返回：[总设计与状态说明](../../project-design.md)。

## 1. 职责与边界

本模块提供推荐所需的设备背景、游戏身份与配置记录。它不负责预测性能，不自动修改游戏，也不把识别不到的信息补成默认值。

输入：玩家选择的游戏、本地只读探测结果、获取失败后用户补充的回答、可选已有配置位置。输出：不可变的设备快照、游戏安装/版本线索、配置观测与未知项。

## 2. 最少输入与自主识别

正常首次操作只要求玩家选游戏。系统先自动识别下列信息；获取失败、字段缺失或结果有歧义时，主动向用户提问获取所缺信息。影响当前推荐或测试关联的字段优先询问，其他字段可集中提供为选填项，避免逐项打断。

本模块统一流程：**自动获取 → 判断缺失/歧义 → 集中向用户提问 → 保存回答及来源 → 继续处理。** 用户仍不知道、暂不回答或回答不足时，再保留未知、说明影响并按可用信息继续；不因为首次读取失败就直接跳过补充环节。

| 信息 | 使用目的 | 未知时的处理 |
|---|---|---|
| GPU 原名、显存、桌面/笔记本 | 主要检索与技术分支匹配 | 请用户提供/选择显卡及设备类型；显存可选填，仍未知则保留条件策略 |
| CPU、系统内存 | 判断公开证据差异与后续诊断 | 在补充面板选填；确实影响诊断时明确询问，仍未知则限制严格比较 |
| 显示器分辨率与刷新率 | 提供显示背景与目标建议 | 请用户补充显示信息；需要游戏渲染分辨率时单独询问，二者不混用 |
| GPU 驱动、Windows 版本 | 复现与版本风险 | 先请用户补充相关版本，可选不知道；仍未知时注明适用限制 |
| 游戏正式名、发行平台、构建号 | 避免同名/平台/版本混淆 | 请用户确认游戏/平台并补充已知版本；不知道构建号不阻止首次收集 |
| 游戏进程及可执行文件 | 绑定性能日志 | 请用户在候选进程中选择或提供已知游戏文件；仍不明则暂不自动绑定 |
| 实际图形/显示设置 | 关联本机测试 | 读取失败后请用户确认是否按方案设置、有无改动；必要时只问影响本轮判断的设置值 |

游戏名允许正式名与显式别名，不仅用可执行文件名推断游戏身份。

## 3. 推荐的探测策略

### 3.1 Windows 基础信息

推荐使用受控的本地 Windows 查询适配器获取硬件原始信息，先验证 PowerShell/CIM 路线。调用参数由程序维护，结构化返回，不让模型临时生成系统命令。

微软的 `Win32_VideoController` 包含显卡名称、驱动和显示相关字段；`AdapterRAM` 是 uint32，不能独自承担现代独显显存容量的权威读取。先采用已验证的读取方式；仍无法可靠取得时，向用户询问容量，回答不确定则保留“未知/冲突”。[微软显卡类文档](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-videocontroller)

系统内存可从系统类提供的字段取得，字段单位必须明确为字节；不把驱动共享内存当成独立显存。[微软系统类文档](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-computersystem)

本章只选择适配路线，未声称目标机器已成功执行这些探测，也不要求为初次搜索安装新驱动或重型依赖。

### 3.2 多显卡与笔记本

- 保存所有探测到的适配器，不直接选择列表第一项。
- 区分“电脑安装的 GPU”和“当前游戏使用的 GPU”；后者需运行时证据或玩家确认。
- 名称中的 Laptop、Mobile、显存容量等信息保留，不能和桌面同名型号合并。
- 无法确定实际游戏 GPU 时，提供一次明确选择；选择前可以并行收集候选资料，主方案保留适用条件。
- 笔记本功耗档、电源状态未知时不擅自补 TGP，也不把桌面测试 FPS 当成本机预测。

### 3.3 游戏识别

首版推荐“游戏目录/库清单辅助发现＋玩家选择”，不承诺全盘扫描和所有商店自动识别。已安装游戏线索与玩家实际选中的游戏分别存储。

构建号来源记录为平台信息、文件版本、游戏内显示或玩家填写。文件版本与游戏公开更新版本未建立映射时，作为不同原始标识保存。

## 4. 游戏适配器

一个游戏适配器描述：规范名称与别名、已验证进程匹配方式、配置文件候选位置、可读字段、值转换表、已验证版本范围和读取限制。

适配器能力分别报告 `can_identify`、`can_read_config`、`can_bind_capture`，不使用“支持此游戏”一个布尔值代替全部能力。

首个 FH6 适配器的路径、字段与当前版本对应关系尚待只读验证。本设计不根据文件名经验写出并声称可靠的 FH6 配置解析方案。

## 5. 三种配置必须分开

| 对象 | 含义 | 是否等于生效值 |
|---|---|---|
| RecommendationVersion | 系统建议玩家设置什么 | 否 |
| AppliedConfiguration | 玩家声明本轮采用什么，也可记录确认过的原配置基线；不要求已有推荐 | 逐字段保留玩家确认与观测级别，关联版本不等于全部生效 |
| ConfigurationObservation | 程序实际读到了什么 | 只证明读取位置/时间的值，运行时生效仍可能需验证 |

例如，文件中看到 High，而游戏要求重启生效：应记录文件值 High、`activation_state=restart_pending/unknown`，不能直接据此判定当前进程已用 High。

每个配置项记录 value、status、observed_at、method、source_ref、activation_state。status 至少区分 `observed`、`player_confirmed`、`unknown`、`conflicting`。

## 6. 推荐的玩家确认流程

此流程是新增推荐，用户此前尚未单独确认。

1. 玩家查看方案，手动修改。
2. 返回点击“已按方案设置”，生成 AppliedConfiguration 版本。
3. 默认继承该推荐的明确设置值，标为 player_confirmed；条件未落实的项继续未知。
4. 玩家有自行修改时只记录差异，不重新填写整张表。
5. 能可靠读取的项自动对照；发现冲突集中展示，暂不生成严格因果比较。

玩家点确认代表声明，不改写为程序自动读取成功。不确认也允许保存反馈，但相应 Session 标记配置未核实，不能作为高确定性的设置效果证据。

### 6.1 原配置基线与未知配置

- 玩家尚未采用推荐时，可选择“记录当前配置为基线”。可靠读取的内容先作为ConfigurationObservation展示，玩家确认实际采用情况后创建 `origin=baseline` 的AppliedConfiguration，recommendation_id=null；保留逐字段来源和生效状态。
- 可只确认影响当前测试的字段，其他项为unknown。只知道预设名时保留预设引用及已知自定义差异，不根据预设名推测未核实的菜单值；若无法确认预设内容/版本，只作有限比较。
- 不知道或不愿确认配置时仍可创建Session、采集/导入日志并提交反馈；applied_id=null、configuration_state=unverified。不得创建一份假“已采用配置”来满足外键，也不继承最新推荐。
- 后补信息创建新版本，明确它是否适用于过去会话及时间范围；只有得到该时段的依据才能通过追加绑定事件关联过去区段，原先未知状态与修订历史仍保留。确认当前配置不能自动证明过去相同。

### 6.2 调整、手动改动与恢复

采用反馈调整时，以ChangeSet绑定的实际配置A为基础生成B；B保存 `parent_applied_id=A`、`change_set_id` 和完整合并快照，不从最初推荐重新继承。未改字段及其未知状态原样保留，新会话显式绑定B。

提交携带expected_current_applied_id；当前配置已被其他操作改变时返回版本冲突，先核对差异，再基于新版本生成调整，不静默覆盖。玩家顺便改动的其他项必须记录，此时实验按实际差异降低归因级别。

“恢复”仍由玩家在游戏中执行，完成确认后创建origin=rollback的新版本，父版本为恢复前当前配置，restored_from_applied_id指向恢复目标。只打开历史方案不改变当前采用版本。详细事务与接口见[第07章7.1节](./07-data-and-architecture.md#71-调整采用与并发检查)。

## 7. 游玩中的修改

- 已知修改时建立新的 AppliedConfiguration；不要改写原版本。
- 若有准确时间，当前会话分成多个区段，各自绑定配置版本。
- 只知道“中途改过”但不知道时间时，会话标记 mixed_configuration；可展示总体体验，不用于该设置的严格前后比较。
- 游戏更新、驱动变化、分辨率或帧生成变化都触发新环境/配置快照检查。

## 8. 失败与降级

向用户提问是自动获取失败后的正式获取路径；下表中的保留未知或能力降级，仅在用户无法补足之后采用。该规则仅用于本机设备、游戏身份和实际配置，不把公开攻略搜集转交给用户，也不新增检索前目标FPS/画质偏好的必填项。

| 问题 | 降级方式 |
|---|---|
| 硬件查询不可用 | 主动询问显卡和已知设备信息；回答后继续，未提供项保持未知 |
| 多 GPU 无法判定 | 询问当前游戏使用哪张显卡，可直接选候选项；不确定时保留条件 |
| 无游戏配置适配器 | 提供清单，询问采用情况及自行改动，不要求重填全部设置 |
| 部分字段读不到 | 列出缺失项，请用户补充；保留已读字段，未能补齐的项继续未知 |
| 游戏版本不明 | 询问用户已知版本/发行平台；无法提供则继续资料收集，版本敏感分支暂缓 |
| 配置已写但未生效 | 询问是否重启/重新进入游戏，记录用户回答与 activation_state |

### 8.1 提问方式与回答记录

- 说明未取得什么、为什么需要，以及用户可以回答什么；候选明确时优先选择题，同时允许自然语言输入。
- 示例：“未能自动读取你的显卡。请提供显卡型号；如果知道，也可补充显存容量和台式机/笔记本。”
- 将关联缺失项集中呈现；有明确回答后不重复询问，用户可以修正之前的信息。
- 用户可回答“不知道/稍后补充”；非关键字段不阻塞其他处理，关键未知则说明哪些推荐或比较暂不能确定。
- 保存字段值、用户原话、回答时间和 `method=user_provided`；配置采用确认继续使用 `player_confirmed`。都不改写为 `observed`。
- 用户回答与自动读取冲突时保留两份依据，向用户说明差异并确认本轮使用的信息，不能静默覆盖。

补充面板通过持久化InformationRequest关联任务。回答或明确跳过后生成新快照/配置，并返回后续任务状态；未回答不能当作跳过。等待、过时回答、幂等重试和新输入修订规则统一见[第07章8.1节](./07-data-and-architecture.md#81-补充信息的回答与继续处理)。

## 9. 本模块验收

自动获取失败会触发适当补充提问，回答能进入后续流程；多 GPU 不误选；笔记本不合并桌面；用户不知道时不补猜测；桌面分辨率不冒充渲染分辨率；用户提供与自动观测可区分；推荐与采用分开；中途修改不覆盖历史；一次确认不被表述为自动验证。每一项有可重现输入与预期输出。

新增验收：无推荐也能保存原配置基线；配置未知能保存会话/反馈；后补当前信息不自动回填历史；连续两轮局部调整保留先前自定义值；过期采用提交返回冲突；查看历史与确认手动恢复有不同结果。
