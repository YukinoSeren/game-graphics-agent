# 04 本机性能采集、指标与比较设计

> 推荐设计 v1.0；本轮只核对文档，不安装或启动性能采集工具。  
> 返回：[总设计](../../project-design.md)。

## 1. 首版路线

推荐先实现一种经过验证的 PresentMon CSV 导入，再接本地引导采集。导入入口作为工具权限不足时的降级方案保留；其他日志格式各用显式适配器，不能只按类似列名猜单位。

PresentMon 官方控制台文档提供按进程过滤、CSV 输出、热键/定时采集，以及不同指标格式。字段随版本和选项变化，某些帧类型或输入相关数据要求额外支持。因此本项目必须保存工具版本、选项和实际列，而不能承诺每个游戏都能得到全部指标。[官方控制台文档](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md)

## 2. Session 先于采集建立

一次 Session 保存：game_id、DeviceSnapshot、AppliedConfiguration、推荐版本、场景说明、工具配置、时间范围、FG/超分/分辨率背景、采集/配置可信状态。

启动采集前程序建立本地 Manifest；结束后把原始日志哈希、进程、交换链选择和时间信息写回。玩家外部导入日志时，系统做候选关联，无法可靠确认则集中请求一次绑定。

日志文件名或修改时间不能单独证明对应某套配置。进程重启导致 PID 变化时生成新采集区段，保留启动时间以避免复用 PID 错配。

## 3. 正常采集操作

1. 选择已有推荐/实际配置版本。
2. 玩家在游戏中进入场景，点击开始或使用已配置热键。
3. 后台只记录目标进程与已确认交换链，保存开始时间。
4. 玩家结束或达到定时时长，关闭本次采集。
5. 程序校验日志，生成摘要；玩家补充简短反馈。

权限不足时显示具体可用降级，不自动提权，也不自动停止玩家其他采集会话。自己的采集使用独立任务/会话标识，取消只终止本任务。

## 4. 场景协议

首轮优先推荐游戏内置测试，或一段可重复路线。建议基线测试在热身后采集60—120秒；这是课程原型的初始测试协议，可按游戏调整，不是通用统计充分性保证。

保存路线/存档位置、天气/昼夜、视角、分辨率、FG状态及已知游戏版本。游戏无法控制天气等条件时标记差异，不伪装成严格相同场景。

普通玩家可以一次采样获得初步观察；要宣称设置改善，应推荐相同协议重复测试，验证阶段每配置至少3次。自然游玩可以积累体验与异常线索，不能自动替代受控比较。

## 5. 统一帧记录

| 字段 | 含义 |
|---|---|
| session_id / segment_id | 所属会话和场景/配置区段 |
| timestamp / time_basis | 相对或绝对时间及单位 |
| process_identity / swapchain_id | 实际捕获对象 |
| frame_stream_kind | application_present、displayed 或 unknown |
| interval_ms | 本流相邻事件的间隔及明确定义 |
| frame_type | 应用渲染/生成/未知，只有来源能识别时填 |
| gpu_busy_ms / cpu_busy_ms | 可选的该帧相关计时，不当成整机利用率 |
| dropped / validity | 原工具报告及本地校验状态 |

导入适配器保存 `source_column_map`、单位、转换方法与分析器版本。无法确定帧流类型时，只显示“该工具报告流”的统计，不冠名本机原生渲染帧率。

## 6. 推荐的首版统计口径

### 6.1 应用呈现流

对同一进程、同一交换链、连续分析区段的 n 个事件，得到 n−1 个有效相邻间隔 d_i（毫秒）。

- 时长：`T = sum(d_i) / 1000`。
- 平均应用呈现率：`F = 1000 * (n - 1) / sum(d_i)`。
- 帧间隔中位数、P95、P99：对 d_i 排序，用 nearest-rank（第 ceil(p*m) 项，m=n−1）定义，保存百分位算法。
- 长帧次数与时间轴：按下述项目定义计算。

不平均每帧的 `1000/d_i`；也不在有未知缺口或删除大段样本后仍用全部帧数/时长。若选择了多个不连续区段，分别计算，并明确有效时长后再汇总。

### 6.2 Low FPS 的口径

首版主报告优先使用平均呈现率和 P99 帧间隔。需要 Low 指标时，明确命名为“最慢1%帧间隔均值倒数”：取最大的 ceil(0.01*m) 个间隔，`1000 / mean(slowest_intervals)`。

它不等于 `1000 / P99`，也不保证和其他工具叫作1% Low的算法相同；外部日志已有1% Low时保留工具口径，不与本地自算值直接混比。0.1%指标在样本不足时不展示；建议至少满足对应尾部有20个样本的项目门槛，否则报告不足。

### 6.3 显示流与帧生成

只有日志明确给出可解释的显示事件/持续时间，适配器验证后才单独统计显示节奏。无可靠 FrameType 时不反推生成帧数量、不把显示流当作原生流。

有FG时同时报告FG开关来源和可测的帧流种类；FG关闭与开启的显示帧数差异不被解释为同等输入延迟改善。没有可靠的输入时间测量时，“不跟手”保持主观反馈，不生成端到端延迟毫秒值。

## 7. 清洗与长帧规则

- 解析失败、非正间隔、重复事件与时间倒退保存错误计数；不静默更换单位。
- 坏事件或未知缺口切断连续区段；不跨缺口拼接新的相邻间隔。公式中的事件数和时长只来自同一有效连续区段，分段汇总另存有效间隔数。
- 多进程/交换链分别处理；无法判定主游戏流时保持待确认，不直接全部合并。
- 启动、加载、菜单、切出和热身区段按明确标记排除，记录原始区间与理由。
- 真实游戏过程中的大尖峰不能因为“离群”被删掉；异常值和格式坏值区分。
- 保留原始日志和清洗 Manifest，摘要可复算。

建议项目初始长帧指标：`d_i > max(50ms, 2 × 区段中位间隔)`，相邻长帧算一簇；保存阈值、次数、时长和发生位置。这个阈值是可调整的分析约定，不等于所有玩家感知卡顿的通用标准。

## 8. 日志质量状态

| 状态 | 条件与用途 |
|---|---|
| valid | 时间、进程、流与必要字段可解释，可做声明范围内分析 |
| limited | 可读但时长/配置/场景或部分字段不足，只作有限观察 |
| invalid | 单位、目标流、时间或关键结构无法确定，不生成确定性结果 |

建议分析区段少于30秒或不足1000有效间隔时至少标 limited；该门槛为调试协议，不当作已证明的统计充分性。

## 9. 比较门槛

比较前检查游戏构建、设备与驱动、场景、分辨率、帧流/FG、实际配置差异、采集与清洗规则。

| 级别 | 用法 |
|---|---|
| controlled | 重要条件一致，只有声明的设置/联动组变化；可进行该范围的对比 |
| approximate | 少量条件无法完全控制；描述趋势和限制，不强因果归因 |
| descriptive | 场景/配置/口径显著不同或不明；只并列展示 |

相同设置重复测试的波动先作为参考。项目可采用 `max(3%, 基线重复测试相对变动范围)` 作为“值得进一步验证”的初始平均率阈值，但它不是显著性检验。只有一次测试时标初步变化，不宣称小幅改善稳定。

公开来源与本机的数据没有统一测试条件时，放在参考区，不能作为本机 A/B 对照。

## 10. 摘要与诊断边界

输出 PerformanceSummary：有效时长/样本、平均呈现率、帧间隔分布、长帧簇、可选计时、清洗记录、质量状态与比较资格。

帧时间可表明节奏问题，不能独自确定着色器编译、CPU、显存或存储是哪一项原因。GPU相关计时可辅助提出假设；缺少对应遥测时不诊断“显存爆了”。平均FPS变好而尾部变差时必须同时报告。

## 11. 失败路径与验收

工具不可用时允许导入已支持格式；导入不受支持时保留原件并说明缺什么，不临时猜列；没有日志时仍可基于体验提出低确定性的建议，但不产出假实测。

验收使用已知时间间隔序列验证公式、百分位、1%口径、单位、断段、多流、FG未知和真实长帧保留；真实目标游戏再验证采集权限与格式。两者均需通过。
