# 05 玩家反馈与持续优化设计

> 推荐设计 v1.0；本机数据闭环尚未实现。  
> 返回：[总设计](../../project-design.md)；前置：[配置记录](./01-device-game-configuration.md)、[性能口径](./04-performance.md)。

## 1. 决策目标

游玩结束后，系统给出以下一个主要动作：

- `keep`：保留当前配置。
- `adjust`：提出一组范围明确、可手动执行的改动。
- `measure`：先进行一项有目的的补测。
- `research`：先补查影响判断的游戏/版本资料。
- `insufficient_evidence`：说明现有数据无法形成可靠方向，保留当前状态。

“每次都改设置”不是成功标准。满意且无明显问题时应收敛；不能为展示 Agent 工作量不断调整。

## 2. 反馈输入

默认只需一个可跳过的简短反馈面板：

1. 总体体验：满意 / 还想改善 / 明显有问题。
2. 可选症状：卡顿、整体帧率低、模糊、闪烁/重影、输入不跟手、局部场景问题。
3. 可选一句话：何时发生、最想保留什么效果。

不是每次强迫填写所有症状。自然语言由模型归类，保存原文、结构化解释和 `explicit/inferred/uncertain` 状态。模型归类不等于玩家明确表达偏好。

症状记录至少含：类型、严重程度（玩家提供时）、发生范围、时间/场景线索、对比对象、证据来源。没有时间戳时，不把某次尖峰强行对应到玩家一句“刚才卡了”。

## 3. 偏好逐步形成

明确表达的“必须保留光追”“优先减少模糊”可成为下轮约束；从一次选择推断的倾向先记为 tentative，只作弱参考。多次接受与拒绝记录后，系统可以提出确认，不静默建立永久偏好。

偏好范围分为当前实验、当前游戏和全局。一个游戏中接受较低画质，不自动变成所有游戏的性能优先。

建议目标未被玩家接受时仍是系统提议，不能以“未达到系统目标”否定玩家已满意的体验。

## 4. 先验证本轮数据能回答什么

分析前检查：是否有实际配置记录、是否中途改过、日志是否有效、场景是否已知、与上次是否可比、是否有版本/驱动变化。

| 数据情况 | 允许的判断 |
|---|---|
| 只有文字反馈 | 可提出有来源的排查与低确定性调整，不给本机实测数字 |
| 有日志但配置未知 | 可描述节奏问题，不能把效果归因到某设置 |
| 配置明确但场景不同 | 并列趋势，不宣称受控改善 |
| 同配置重复出现同类问题 | 支持问题可复现，原因仍需验证 |
| 受控前后测试 | 可比较本次变更的局部效果，保留波动和限制 |

## 5. 症状到假设

下面是排查结构，不是预置游戏因果规则。具体改哪个游戏设置仍需知识包支持。

| 症状 | 优先看什么 | 不能直接断定什么 |
|---|---|---|
| 整体帧率低 | 帧间隔、目标流、限制器、分辨率/FG状态、可用GPU计时 | 仅凭FPS就认定显卡瓶颈 |
| 平均帧率尚可但偶发卡顿 | 尖峰时间、场景切换、重复性、版本问题、可选资源遥测 | 没有显存证据就认定显存不足 |
| 模糊 | 输出/渲染分辨率、超分/动态分辨率、运动模糊与作者视觉说明 | 普遍把纹理降档当成模糊解决方案 |
| 闪烁/重影 | 具体对象和运动、抗锯齿/重建/FG状态、已知版本线索 | 没有对比就断言某厂商技术有缺陷 |
| 输入不跟手 | 玩家感受、FG/同步/限制策略和可用输入测量 | 用显示FPS证明输入延迟已经改善 |
| 特定场景掉帧 | 场景标签、当前设置与该效果的测试覆盖 | 用白天测试否定夜间效果开销 |

每个假设保存：支持证据、反例、缺失信息、可检验动作、预期观察及替代解释。优先选择“证据更直接、改动更小、可恢复且能区分原因”的动作，而不是输出一长串通用优化清单。

## 6. 生成调整实验

默认一个设置，或必须一起修改的依赖组；最多再给一个备选方向。必要联动组整体记为一个实验单元，不能分别宣传其各自收益。

ChangeSet 必须包含：

| 字段 | 内容 |
|---|---|
| base_applied_version | 实验前实际配置 |
| changes | 原值、建议值、原值的确认状态 |
| hypothesis | 要验证的问题，不先写成已证实原因 |
| evidence_refs | 来源实测、官方约束或本机结果 |
| expected_direction | 性能/画质/延迟的预期方向，可为未知，不捏造量值 |
| protected_preferences | 本轮不得破坏的明确偏好 |
| dependencies / restart | 联动、必要生效条件 |
| test_protocol | 推荐相同场景与可测指标 |
| rollback | 恢复哪一版本及可执行步骤 |

若原值未知，先补确认影响实验的少量字段，不能生成假回滚值。玩家自行改动其他设置时，实验降级为 approximate/descriptive。

## 7. 评价一次改动

| 结果 | 建议 |
|---|---|
| 玩家满意，性能无明确退步 | 保留，并存为当前个人方案 |
| 性能更好但玩家不接受画面 | 恢复或试另一方向，不能仅因FPS高而称成功 |
| 画面改善，代价在玩家可接受范围 | 保留，即使FPS略降 |
| 改善小于重复测试波动或只有一次样本 | 标记未定，建议补测或保留较简单方案 |
| 平均更高但尖峰更多 | 同时报告，按症状与体验决定，不只看平均 |
| 结果相反或明显更差 | 解释反证，建议恢复，不连续叠加更多猜测 |

Outcome 采用 `accepted/improved_but_rejected/no_clear_change/worse/inconclusive`，保存指标变化、比较资格、玩家接受情况和依据。`accepted` 表示玩家接受，不自动等于统计显著改善。

## 8. 停止规则与避免循环

- 玩家满意且没有主动要求继续：建议维持。
- 已达到玩家接受的目标、改进空间主要依赖明显画质牺牲：展示取舍后维持。
- 连续两轮受控尝试没有清楚改善：建议暂停或转针对性诊断；这是产品建议阈值，可调整。
- 数据不足：补测应回答具体问题；不让玩家无目的重跑。
- 重复提出已验证无效/已拒绝的改动：必须说明新版本/新证据，否则不再推荐。
- 玩家选择暂不测试：保留方案与缺口，允许正常使用。

停止优化不会删除旧记录；版本更新或玩家提出新问题时可以启动新一轮。

## 9. 无需玩家额外搜集的默认路径

Agent 先利用现有日志、公开资料、设置依赖和历史。只有无法推断且会改变建议的本机事实才集中请求，例如“本轮是否开过帧生成”。不要求玩家复述所有硬件，也不要求逐项菜单截图。

## 10. 示例闭环

以下为虚构诊断流程：玩家说“画面满意，夜间偶尔卡顿”。系统确认本轮配置与夜间区段，发现该区段长帧明显；知识包只有白天阴影测试，不能直接推出夜间阴影应降低。

系统先查夜间场景和当前版本线索；若取得有条件的夜间开销证据，提出仅改变相关阴影组的实验，保持玩家重视的其他效果。相同路线复测后比较长帧与体验。若玩家不满意画面或没有改善，恢复并保存无效尝试。

## 11. 验收重点

有反馈无日志不造数字；配置不明不强因果；满意可维持；失败实验可恢复；一次只改可解释的组；玩家偏好不被模型猜测永久覆盖；本机结果不泛化到其他人；版本变化不会抹掉旧经验。
