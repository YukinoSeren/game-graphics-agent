# 06 玩家流程与交互设计

> 推荐设计 v1.0。定义功能与信息结构，不生成前端代码或像素稿。  
> 返回：[总设计](../../project-design.md)。

## 1. 产品形态

推荐 Windows 本地网页界面：玩家启动本地程序后在浏览器使用，后台管理设备探测、采集、模型和本地日志。首版不要求注册账号；游戏和历史按本机用户保存。

在做成完整桌面壳之前，先验证使用流程是否成立。网页不会独立读取硬件；能力由本地后台提供。

## 2. 默认旅程与玩家操作量

| 阶段 | 玩家默认操作 | 系统自主处理 |
|---|---|---|
| 首次设置 | 配一次模型服务；选择游戏 | 探测可读硬件，检查服务与游戏能力 |
| 收集 | 点击开始后等待；可离开页面 | 复用/发现来源、提取、核验、补查、保存 |
| 看推荐 | 阅读主方案，需要时展开替代项 | 解释取舍、出处、未知和建议目标 |
| 应用 | 在游戏中手动设置，返回一次确认 | 保存采用版本，可靠读取时核对差异 |
| 游玩 | 正常玩；测试时启动/结束采集 | 绑定日志，校验并生成摘要 |
| 反馈 | 可选总体满意度和一句话症状 | 关联证据，建议维持/调整/补测 |

不在入口强迫玩家选 FPS、预设画质或 RT 偏好。主动填写的偏好可保留为可选输入。

## 3. 页面与信息结构

### 3.1 游戏与设备页

显示游戏选择、检测设备摘要、上次知识更新时间与能力级别。只突出会影响当前推荐的未知字段。多 GPU 歧义集中显示一次选择，其余高级设备字段折叠。

自动获取失败后主动打开补充面板，说明缺失项和用途，允许选择候选或自然语言回答。用户提供后继续，已成功取得的字段不要求重填；“不知道/稍后补充”保留未知及相应限制。

主要动作是“分析这款游戏”。可选“说明我的需求”，不作为继续操作的必填关卡。

### 3.2 收集任务页

展示阶段、有效来源、已覆盖内容、关键缺口、实际调用和最近活动。使用阶段进度，不用虚假的“完成87%”。系统无法估时就显示已耗时及正在解决的问题。

提供取消并保留成果、查看部分结果、稍后继续的入口。后续断点恢复能力未实现前，界面必须明确“保存结果，稍后新建补查任务”，不能显示已支持自动续跑。

### 3.3 推荐页

页面默认信息顺序：

1. 主方案结论、适用设备与 actionable/provisional/blocked 的人类可读含义。
2. 建议目标和参考实测，明确本机尚待验证。
3. 按菜单分组的设置清单及必要操作。
4. 影响决策的待确认项。
5. 偏画质/偏性能替代调整。
6. 展开后查看原文出处、测试条件和分歧。

设置表建议列：设置、建议操作/值、与当前的差异、主要理由、证据/状态。长说明展开，不用一大段聊天代替可操作清单。

`keep_current`、条件项与未知分别显示，不用空白或灰色数值冒充已确定值。“复制清单”“导出 Markdown”方便玩家对照菜单。

### 3.4 本轮配置与采集页

显示实际采用版本、自动读取与玩家确认的字段区别。主要动作“已按方案设置”，次要动作“我有几项改动”。对必须重启的已知项单独列出。

测试区域显示目标游戏、采集状态、协议简述与开始/结束。切换场景和中途修改可标记区段。工具不可用时提供受支持日志导入入口。

### 3.5 结果与反馈页

先给结论：本次数据质量、体验和建议动作。随后展示本机指标、帧时间时间轴及与可比轮次的变化。公开参考放在独立区域，避免和本机数据画成同条件 A/B 图。

反馈可跳过；有问题时显示症状选项和一句话输入。调整建议同时给原值、新值、依据、测试方式和恢复入口。

### 3.6 历史页

按游戏展示推荐版本、采用版本、测试区段、体验及结果。可选两次记录比较；不满足比较条件时解释差异，并保留并列查看。

旧方案因更新需复核时保留可读历史；恢复指“查看并手动恢复该方案”，不触发尚未支持的配置自动写入。

## 4. 状态与具体文案

| 情况 | 推荐表达 |
|---|---|
| 同卡证据不足 | “主要参考邻近设备，具体表现待本机验证” |
| 方案有关键未知 | “已有参考方案，以下条件尚未确定” |
| HDR 只读到检测信息 | “资料未给出 HDR 开关建议，保留当前值/待确认” |
| 测试配置不清 | “可以展示本次性能，暂不能归因于某项设置” |
| 预算停止 | “已保存成果，仍缺这些信息；可继续补查” |
| 模型不可用 | “当前无法完成提取/推荐，已有资料已保存” |
| 满意无需改动 | “建议保留当前方案” |

玩家页面不展示 records/foreign keys 等工程字段。详细诊断日志在开发模式，不让用户为接口报错理解内部实现。

## 5. 最少必要询问

系统决定询问前记录三个理由：该事实会改变什么建议、能否自动取得、缺失时能否条件化交付。只在确实必要时提问，优先集中在同一处。

设备、游戏及实际配置自动获取失败时，按第01章将补充提问作为正式路径，优先问关键缺失项，其他项选填；用户回答与自动读取分开标记。该路径不要求用户自行搜集网页资料，也不提前要求FPS或画质目标。

允许玩家选择“暂时不知道”。界面清楚标注因此受限的结论，其他功能继续可用。不能把所有缺失环境条件变成必填表单。

## 6. 可视化约定

- 帧间隔用时间序列，显示区段、长帧、已知改动和加载排除范围。
- 同口径比较使用同单位与轴标，不能把 FPS 和毫秒放在无说明的同一轴。
- 没有视觉量化依据时用作者描述和取舍表，不画虚构画质得分雷达图。
- 数字须标来源与统计口径；不同FG/帧流条件明显注明。
- 状态除颜色外还用文字/图标；表格、展开和主要动作支持键盘。

## 7. 页面视觉的推荐方向

面向玩家在桌面上查看较密集的设置与结果，以可读表格、清楚状态和逐步展开为主。浅/深主题跟随用户选择，避免强制“游戏工具必须深色”。

本稿不锁定品牌色、字体和像素级组件。这些不影响闭环决策，可在用户认可产品流程后另做视觉规格；不因此把本稿描述成已经完成前端实现。

## 8. 异常与恢复

刷新页面保持任务；断网显示已有结果；服务失联不重复提交同一采集；取消不丢弃成果。无法读取配置、无法采集、数据不足分别给不同降级入口。

玩家不会因为模型失败被迫重新设置游戏、重新确认全部硬件或重跑已经有效的测试。

## 9. 交互验收

从选游戏到看到建议不需要先选FPS；来源收集无逐页人工参与；推荐能直接按菜单操作；应用确认与程序读取有明确区别；错误能继续/退出；普通旅程无需看原始JSON；历史能解释每次为什么调整或维持。
