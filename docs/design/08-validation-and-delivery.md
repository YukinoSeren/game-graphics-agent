# 08 验收、效果评价与交付设计

> 推荐设计 v1.1；增加设计审查五项问题的可重现验收。门槛是未来验收要求，不是已达到的准确率或改善结论。
>
> 返回：[总设计](../../project-design.md)。

## 1. 分开回答四类问题

1. 程序是否正确执行规则：类型、引用、统计、状态与预算。
2. 网页是否被正确提取：值、条件、位置、配置—环境—指标关系。
3. 推荐是否自洽、可操作：合法值、支持条件、完整动作与证据。
4. 本机使用是否有价值：性能/体验取舍、试错成本和玩家满意度。

不能用程序单元测试通过证明网页全正确，也不能用作者推荐正确摘录证明玩家机器优化有效。

## 2. 当前证据基线

已有采集代码、45项离线测试，以及一次真实Dot Esports资料中24个选定固定值一致、3项语义保留检查通过。最终该运行接受89条、隔离3条，仍为部分结果。

这些是历史已见样本的调试/回归结果，不是独立准确率。四篇既有评测尚未全部通过自动逐项回归，其他模块主要还在设计。新测试需注明代码/模型/提示/Schema版本，不能不断改答案后仍称原来的盲测。

详细基线见[首轮实施报告](../../collector-implementation-report.md)。

## 3. 需求到验收映射

| 编号 | 要求 | 核心验收 |
|---|---|---|
| C01 | GPU为主且保留关键环境 | 同名桌面/笔记本不误配；显存未知可保留条件 |
| C02 | 不以目标FPS/偏好作为入口关卡 | 只有游戏和可用设备信息也能开始完整收集 |
| C03 | 自主充分收集、减少参与 | 玩家不必逐页截图；补查有理由，预算停止保留成果 |

| C05 | 邻近硬件可条件参考 | 说明迁移依据，不能把源FPS当本机预测 |

| C07 | 玩家手动配置 | 系统无隐式写游戏/驱动参数 |
| C08 | 长视频暂缓、图片单独标记 | 未读图片不宣称覆盖图中数据 |
| C11 | 第一部分自动获取失败后向用户提问 | 提问明确、回答能继续、已知项不重填、不知道可保留、来源标记不混淆 |

### 3.1 本轮设计修订与回归验收

下表为未来实施必须验证的用例，不代表本轮已有对应程序或测试通过。配置字段采用抽象夹具，不声明任何FH6实际菜单/取值。

| 编号 | 可重现输入/操作 | 必须观察到的结果 |
|---|---|---|
| D01 调整采用链 | A包含推荐外的纹理High，C1只改阴影，确认得到B；C2再基于B改另一项；以旧A提交过时调整；最后手动恢复并确认 | B及后续版本保留纹理High和未改字段；新版本关联父版本/ChangeSet，复测及Outcome绑定正确版本；过时提交409且不推进当前指针；回滚另建版本并保留失败记录 |
| D02 创建幂等 | 对知识/推荐/采集/导入/补充回答/结果及恢复入口，模拟同key并发、成功响应丢失、后台重启后重试、同key不同输入、同Session不同key重复采集 | 每个逻辑提交仅注册一个任务/结果，外部调用桩不因请求重试重复启动；相同提交返回原ID，不同输入409；活动采集冲突返回原任务；计费状态未知不隐式重发；清理结果后的旧key返回410 |
| D03 独立基线与未知配置 | 无推荐时保存原配置/预设引用；另建applied_id=null的会话并导入有效日志、反馈；随后只确认当前配置 | 基线recommendation_id=null，未展开预设项仍未知；无配置会话可保存并受限分析，不冒用最新推荐、不作controlled归因；当前确认不自动回填过去区段 |
| D04 回答后继续 | 探测失败生成问题；部分回答并刷新；用新key提交下一批回答/明确跳过剩余项；原key重试；上下文变化后提交旧回答；对已结束任务后补 | 已答项不重问、关键未答项维持waiting_input并释放工作队列；回答/明确跳过后新输入修订与新快照关联，必要时继续为有限结果；重试不重复版本；过时回答409，失效问题有替代或解除等待；后补不重启终态任务 |
| D05 长帧比较 | A/B中位间隔16/40ms，各有60/70ms尖峰；共同阈值50ms；另测60秒2簇与120秒4簇、恰等阈值、零时长及未知缺口 | 自适应计数差异不被称为改善；共同阈值下两类尖峰均计入；发生率均2簇/分钟；等阈值不计入，零时长为null，缺口不拼簇；保存阈值/分母/协议；无法统一时只降级对应指标 |

每个用例记录输入版本、操作序列、对象/任务数量及预期状态；创建幂等用受控的供应商/采集适配器计数验证，不通过反复付费调用来测去重。

## 4. 网页抽取与知识层评估

### 4.1 回归集

完成现有四篇文字评测与官方更新样本映射，逐项检查固定值、条件/候选、HDR观察、FPS区间、硬件/场景/版本、矩阵列和更正。

分别记录：字段正确/遗漏/多提、关联正确/错误、条件保留、原文定位有效、来源问题识别。每个指标有分母，不能只报“整体95%”。

关键错误零容忍：把不支持技术交付为可执行建议；把未知补成确定值；跨表列/场景配对；编造测量；把观察改为开关建议。这是验收门槛，不是预先承诺模型永不出错；一旦发现则修复或正确隔离。

### 4.2 未见测试

建议至少新增不同作者/版式的文字资料，再选一款第二游戏作为迁移样本。先冻结模型输出与版本，再由不依赖输出答案的标注流程核对。若只由同一模型回查，明确叫一致性检查，不报告独立泛化准确率。

抽取率与隔离率同时报告：全部隔离不能被包装成“无错误”，全部接受也不等于高质量。

## 5. 推荐层评估

构造并验证：同卡充分证据、同卡不足、显存差异、笔记本差异、版本未知/更新、作者分歧、完整方案不足、关键互斥、只有观察没有平均FPS、玩家保留效果、没有足够证据生成替代项。

每个用例检查：

- 推荐动作是否可执行，取值/依赖是否正确。
- 主方案选择是否有可解释依据。
- 综合方案是否被错误宣传为作者已实测整套。
- 暂缓与未知是否落实到具体项，而不是整页免责声明。
- 可追溯设置占比、关键未知数量、冲突处理与人工审阅成本。

非确定性输出允许文本不同，但相同输入下关键支持条件和原值不得漂移。重复运行评估稳定性，不靠一次看起来合理就验收。

## 6. 性能统计与诊断评估

使用受控时间序列验证平均率、百分位、Low口径、断段、长帧、FG未知、多流和单位。对工具导出人工选定区段复算，明确可接受的数值误差。

长帧须分别核对区段自适应定位与共同阈值比较。比较保存阈值模式、实际阈值、基线引用（适用时）、有效时长、簇/分钟及长帧时间占比；按第04章定义复算。若采用基线导出阈值，在查看调整后结果前冻结，不能事后选择更好看的阈值。

诊断用例覆盖：有反馈无日志、有日志无配置、加载段尖峰、真实游戏尖峰、平均改善而尾部退步、配置中途改变、GPU计时缺失、版本变化。预期系统能降级和补测，不凭一个指标下确定原因。

## 7. 本机效果实验

### 7.1 对照条件

至少比较玩家原配置/一个明确游戏预设与Agent主推荐。NVIDIA等外部推荐若可取得且当前环境支持，可作为额外基线；无法取得时不阻塞课程项目，也不伪造其设置。

原配置在手动修改前保存为origin=baseline，可无推荐引用；未知字段和生效条件保留。只记录预设名不等于已掌握完整配置。若关键项无法确认，则记录可得数据并降低比较等级，不能为完成对照而补默认值。

同一设备、已知游戏版本/场景、相同分辨率与采集口径。FG等重要变量变化单独说明。每配置建议至少3次采样，调整顺序或穿插基线以观察热身/场景漂移；资源不足时明确探索性范围。

### 7.2 结果记录

平均应用呈现率、P99帧间隔、项目定义长帧、可用显示流指标；玩家对画面、流畅度、响应和总体方案的接受情况；测试/修改次数及操作负担。

“更快”不是唯一成功：画质明显改善且玩家接受性能代价也可有价值。没有独立质量测量时使用有条件的作者说明与主观反馈，不虚构客观质量得分。

样本只有一个玩家/设备时，结论限制在该环境；展示个案完整闭环，不宣称全型号普适提升。

## 8. 推荐交付里程碑

| 阶段 | 可演示成果 | 退出条件 |
|---|---|---|
| M0 已有基础 | 采集CLI、类型/来源校验、真实运行 | 已有首轮结果，真实回归仍需补齐 |
| M1 知识输入稳定化 | 当前案例可追溯知识包、覆盖与缺口 | 已见资料回归完成；关键错误被修复或隔离，隔离不过度丢弃必要信息 |
| M2 首次推荐 | GPU背景→主方案/目标说明/替代差异 | 兼容/取值/组合检查、逐项出处和未知均可审阅 |
| M3 采用与性能 | 原配置/采用版本或明确未知→日志→可复算摘要 | 进程/场景/配置关联，独立基线、未知配置降级、共同阈值及归一化用例通过 |
| M4 反馈闭环 | 一次keep/adjust/measure决策及历史 | 调整→实际采用→复测→结果引用贯通，连续调整保留自定义值、冲突和恢复用例通过，至少一次真实流程 |
| M5 产品演示 | 本地页面贯通M1—M4 | 正常与失败路径、补充回答接续及创建幂等用例通过，无开发者逐页修复才能完成 |
| M6 迁移评价 | 第二游戏/未见来源 | 明确能力差异，不能把FH6特殊处理当通用能力 |

先做每阶段所需的最薄页面或CLI验证，再形成完整界面；无需等全部后端完成才发现玩家流程不通。具体工期需在用户审阅范围、验证采集工具后估算，本稿不承诺固定天数。

## 9. 完整演示脚本

选FH6与已读设备 → 无FPS前提开始收集 → 展示主推荐、来源与未知 → 玩家手动采用并一次确认 → 进入测试场景、采集/导入 → 反馈一个症状或满意 → 系统给出有依据的调整或维持 → 保存版本 → 可比复测 → 展示结果与是否接受。

同时演示至少一条失败路径：模型失联保留资料、同卡不足条件化推荐、无法采集改用导入，或配置未知限制归因。演示应体现系统知道何时不能断言。

验收另走一次“保存原配置基线→采样→采用推荐→复测”和一次“配置未知→导入→反馈”流程。对adjust分支记录基础A、变更C、采用B、复测区段与Outcome，人工核对未改字段保留；模拟响应丢失后沿用同一提交标识，确认任务ID和调用计数不增加。以上不增加正常入口的目标FPS/偏好必填项。

## 10. 风险与处理

| 风险 | 处理与暴露方式 |
|---|---|
| 网页反爬/内容变化 | 公开替代来源、修订快照、明确访问范围 |
| 模型引用/条件错误 | 类型、定位、关系检查与独立样本；不降低门槛来提高接受率 |
| 配置读取不可靠 | 玩家确认与逐字段状态；首版不依赖全量解析 |
| 日志权限/兼容不稳定 | 先验证目标游戏，保留格式明确的导入 |
| 证据不足以选择唯一主方案 | 条件化交付、指出分歧，允许补测或暂缓 |
| 本机结果不可复现 | 场景协议、重复测试与比较等级 |
| 课程规模失控 | 一游戏完整闭环、单进程、本地用户、后置视频/自动改参数 |

## 11. 设计审阅与后续决策

本稿已给出所有主要缺口的推荐处理，而非要求用户逐项自行设计。后续重点审阅三项产品取舍：首版范围、本地网页形态、采用确认/测试参与量。用户可以整稿认可或修改局部。

事实能力仍需工程验证：FH6配置读取与进程绑定、日志格式/权限、未见资料准确性和真实改善。它们是验证任务，不是可以通过设计文字提前承诺的成功结论。
