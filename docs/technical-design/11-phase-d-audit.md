## 2. 实质问题

### AUD-D-01 / P1：仅复制所选字段与唯一后继规则共同封死其他字段的后续更正

**类型及影响：** 契约冲突/操作入口不完整；影响D-P04、DEV-T04、ENG-T02的问题协调及UX-T02/03。

**准确位置：**

- [01 §5.3](./01-device-game-configuration.md#53-d-p04-已处理问题的关联更正)，第167行：field_paths必须属于直接源问题；第172行：新问题只复制本次选中字段；第174行：每源只允许一个直接更正后继，以后从最新已处理后继继续。
- [shared state §7.3](./shared/state-conventions.md#73-d-p04-更正链与创建原子性)，第270行：重复确认上述唯一后继和从最新后继更正的限制。
- [06 §7.4](./06-player-experience.md#74-d-p04-已处理问题的稍后补充)，第131行：遇已有后继只能转向后继。

**具体失败场景：** 原问题R0有GPU型号和显存两个字段，均已跳过。用户先仅更正GPU型号，创建只含该字段的R1并完成回答。稍后取得当时显存记录：从R0创建更正因已有R1而409；从R1创建更正又因显存不属于R1.fields而422。此后所有后继的字段集合都只能继续缩小，显存永远不能再通过正式更正入口补答。不能通过另改当前上下文解决，因为这会丢失本应保存的原问题更正关系和历史范围。

**现有定义为何不足：** 双修订、唯一直接后继和facts_only零任务写入分别防止了竞态与重跑，但没有保存整条更正链可更正的字段全集。部分回答规则只处理当前请求已有字段，不能恢复已被裁掉的字段。

**最小修订建议：** 保留单链及零源任务写入规则；明确沿amends链可追溯的根问题字段集合，并允许最新已处理后继选择该集合中的字段。逐字段固定原历史上下文/候选依据，不能借回溯读取当前设备值。可通过关联记录保存根定位或在创建时回溯验证，不必恢复旧问题或新增重任务类型。

**补充验收：** 扩充DEV-V08、B-STA-13、UX-V09、VAL-V08：R0有至少两个字段，先只更正其中一个并resolved，再从链头更正另一个，另测第一轮skipped。断言第二字段可达、两个新回答可追溯、无并列后继、旧问题不变；源任务分别running/终态，TaskRun/TaskEvent/TaskInputRevision写入增量均为0。

### AUD-D-02 / P1：未知菜单路径被当成精确身份，可能合并不同本机设置

**类型及影响：** 身份契约不足；影响D-P02、ENG-T01的目录索引、DEV-T02/03及UX-T03。

**准确位置：**

- [01 §5.2](./01-device-game-configuration.md#52-d-p02-本机设置条目登记)，第137行：菜单路径未知可以传[]；第142行：按安装、namespace、raw_name和menu_path精确键无条件复用当前定义，不用raw_text区分。
- [shared data §5.2](./shared/data-contracts.md#52-实际采用与观测)，第261行：同一配置内相同规范设置或原始引用唯一。
- [07 §4](./07-data-and-architecture.md#4-物理存储索引与局部记录)，第72、74行：当前精确键唯一索引及有效头规则。

**具体失败场景：** 无配置适配器时，玩家记得两个不同子菜单中原名都为“质量”的条目，暂不记得完整菜单路径。分别登记raw_name="质量"、menu_path=[]，原话说明一个是纹理选项，另一个是阴影选项，准备分别保存High和Low。按当前规则第二次登记必然复用同一个definition_id；随后两个值成为同一SettingRef的冲突，无法独立保存。若实现覆盖前值则丢事实；若按唯一性拒绝，则“登记两个不同条目→独立基线”没有可表达的入口。

**现有定义为何不足：** 精确字符串相等只能证明提交的定位文本相等；当[]明确代表路径未知时，不能证明两个实际菜单条目相同。“不同menu_path保持独立”覆盖不了两份路径都未知的情形。保留原话、值未知或允许未知配置会话虽能保留有限记录，却不能撤销已经作出的目录身份合并，也不能保存这两个分别已知的值。

**最小修订建议：** 为缺定位的同名条目明确消歧规则：允许用户明确复用已有条目或登记为不同条目，后者由后台分配独立身份/区分键；也可先返回需选择的候选。不要要求伪造菜单路径、改变原名或把自由原话自动当作已核验身份。相应调整未知定位分支的当前键索引；定位足够且明确复用的并发去重继续保留。

**补充验收：** 扩充DEV-V07、ENG-V07、UX-V09：同安装、同player namespace、同原名、路径均未知、用户明确指不同条目的两次登记，最终可保存两个独立值；另测明确选择同一条目仍复用、同key重送不增身份、并发消歧不误合并。更正/补齐路径不能自动迁移旧采用值。

### AUD-D-03 / P1：要求显式替换更正后的设置引用，却未定义可执行的替换输入及合并语义

**类型及影响：** 契约/操作入口缺口；影响D-P02的后续使用、DEV-T03、设置差异校验及UX-T03。与AUD-D-02不同，本项在目录身份完全明确时也成立。

**准确位置：**

- [01 §5.2](./01-device-game-configuration.md#52-d-p02-本机设置条目登记)，第143行：更正生成新definition_id；第144行：新采用若要替换旧引用，必须显式确认新条目及其值/旧值，且禁止在合并时自动将两个ID当成同一真值。
- [shared data §5.2](./shared/data-contracts.md#52-实际采用与观测)，第269行：SettingDeclaration只有一个setting_ref和一个声明值；第273行：调整保留未改项。
- [shared data §9](./shared/data-contracts.md#9-跨模块-dto-与公共调用边界)，第430行：AdoptConfigurationInput只有declared_settings等字段，没有旧引用→新引用替换或移除声明。
- [shared data §7](./shared/data-contracts.md#7-反馈偏好与实验)，第352行：SettingChange也只有一个setting_ref，表示该引用的旧值/新值。
- [01 §6](./01-device-game-configuration.md#6-采用回答与历史补录的关键步骤)，第213行：采用合并玩家差异；[06 §7.2](./06-player-experience.md#72-d-p02-本机条目与基线)，第117行：目录更正不自动修改配置ID或复制值。

**具体失败场景：** A含L1=High、自定义项K和未知项U。只更正L1的菜单位置，得到同series的L2。玩家确认实际值仍为High，希望新当前配置B使用L2，并保留K/U及A的旧引用。现有提交可以声明L2=High，却无法明确说“仅移除A中的L1，并以L2代替”：若按差异追加，L1仍留在B；若按版本族自动替换，违反显式确认边界且缺少声明旧引用的规则；若把declared_settings当全量替换，又没有定义缺席项是否应删除，可能误删K/U。

**现有定义为何不足：** parent_definition_id只解释目录谱系，文档明确说它不证明值事实。expected_current_applied_id能检测当前指针竞态，但不能表达引用替换意图。重新记录一份baseline是否允许全量替换、如何保留未提交项也未被定义，不能作为已存在的确定解决路径。

**最小修订建议：** 在01明确一种正式的显式替换语义。例如为采用声明增加旧SettingRef→新SettingRef关系，要求基于固定base、重新确认新值，并在当前指针事务内只替换指定引用；或者明确定义一个不含歧义的完整快照提交分支。未列入替换的项保持原样；目录更正本身始终不迁移值，旧A/旧摘要/旧SettingRef不变。新增请求字段按共享版本/幂等规则处理，不能悄然改变旧请求的合并含义。

**补充验收：** DEV-V07/DEV-V04增加“已采用L1→目录更正L2→显式确认替换→B仅有L2且K/U保留”；验证未确认替换时不自动删除L1、旧值/当前base冲突零部分写、跨安装替换拒绝、恢复旧名称后仍用新ID确认、旧A可原样读取并作为手动恢复依据。
